Surface 07

Form view — the mode that writes

Every other mode reads rows. A form creates them, which makes it orthogonal to the view list rather than another entry in it. Labels and help resolve through a fallback chain, so a form is usable the moment it is created and configurable when it is not.

Two labels above are overridden, three are not. Title and Author use the column names verbatim. Where can I find it? overrides a column called Source, because a header is terse by necessity and a form label can afford a sentence.

Why the overrides live on the view, not the column

The column description is written for the AI that maintains the table. Form help is written for whoever is filling it in. Same column, different audiences — so the default is a convenience and the override is a requirement.

column.name→Status
column.description→Pipeline stage; set 'blocked' only when waiting on someone else (AI-facing)
view.config.label→How urgent is it?
view.config.help→No pressure either way (submitter-facing)

The whole form config fits in DataView.config, which is already Json — field order, per-form required, hidden fields, prefills, submit text. No schema change beyond mode = "form". Published forms are deferred: anonymous writes raise createdBy, rate limiting and spam handling that private forms simply do not have.

Surface 08

View access, and the split mode

Two additions from looking outside Notion. Airtable puts an access model on every view — one enum column, and it replaces the localStorage preference we had planned. Split is a desktop idiom neither product has.

Replaces O10. A personal view becomes a nameable, keepable, later-shareable object rather than a preference hidden in localStorage. Notion charges for this; Airtable made it a property of the view.

Split — read through a table, not across it

Rows on the left, the selected row on the right. Mail clients, Obsidian. Grid is for editing across rows; split is for going through them one at a time — which is what a reading list or a contact table is actually for. Nearly free: both halves already ship in Phase 2.

Ledger

What this preview decides

Each row is an open decision from the plan, answered by something visible above. Disagree with any and the change is a CSS edit, not a refactor.

O1
"Data Table" or "Database"?
Database — used throughout above. It has views, relations and rollups; the stub's wording predates all three.
O2
Query mode before relations?
Yes — Surface 05 reads as the same product as Surface 01, which is the whole argument. It also proves the view layer decoupled cleanly.
O4
Column type changes: coerce, or forbid?
Forbid — the type picker in Surface 03 is display-only. Create a new column and migrate.
O5
Undo: in-session real, durable stubbed?
Build it. Skipping does not save the work — DataRow.deletedAt already exists, so without undo you build a row trash-and-restore screen instead, which covers deletes but never cell edits or pasted ranges.
O13
Form view
In scope. Private forms in Phase 2; published forms deferred behind their own pass — anonymous writes raise createdBy, rate limiting and spam handling.
O14
View access model
Adopt Airtable's personal / collaborative / locked. One enum column, and it replaces O10's localStorage preference.
O16
One window node, or a separate database block?
Extend noteWindow. Its targetContentId is already kind-agnostic, and it has solved cycle detection, depth limits, blockId hygiene, presence gating and public-render UUID safety. Gated on reading its 1,033-line node view first.
O8
Second view mode: kanban or gallery?
Both, and list too. Board is the one that earns the phase; the other two fell out nearly free once the view layer existed.
O9
Views in the tree: virtual or real nodes?
Virtual — the dot markers in Surface 04. Real nodes would hand views tags, links, trash and grants nobody asked for.
O10
Per-user view memory
localStorage, not schema. Notion charges for personal views; this costs nothing and needs no migration.
O11
Tree order for promoted rows
Stamped once from the default view at promotion, then independent. sortKey is per-view, so continuous sync is not even well-defined — but it does mean reordering the table will not reorder the tree.
