## #223 — Shortkey for closing a tab doesn't fully close out a tab

**Reported:** 2026-09-12 · **Labels:** `bug`

**Symptom.** The close-tab shortcut clears the content and shows a loading skeleton, but
the tab stays in the pane's tab rail (reporter's screenshot: a daily note, "Sept 11, 2026").
Expected: the tab goes, and the pane falls back to the previously viewed tab.

**Where it lives.** The shortcut handler is
`components/content/headers/MainPanelHeader.tsx:662-684` — a `window` keydown listener,
gated on `isActivePane`, bound to Cmd/Ctrl+Alt+W and Cmd+Ctrl+W (plain Cmd+W never reaches
the page). It calls `closeContentTab(activeTabId)` at
`components/content/headers/MainPanelHeader.tsx:679`.

That is **the same reducer the X button calls** (`MainPanelHeader.tsx:911`), which is the
central fact of this bug: the close path itself is shared, so the divergence is not in
`closeContentTab`.

Three things I ruled out by reading the code:

- **The rail cannot show a phantom tab.** It renders strictly from `pane.tabIds` →
  `tabsById` (`MainPanelHeader.tsx:399-405`, mapped at `:778`), and `closeContentTab`
  deletes from both (`state/content-store.ts:2189-2203`). A tab visible in the rail is a
  tab that exists in the store, so the reported tab was **re-created**, not left behind.
  The loading skeleton agrees — that is a fresh content load.
- **The URL is not stale.** `syncBrowserState` deletes `?content` and the `tabs_*` params
  and clears `lastSelectedContentId` (`state/content-store.ts:1474-1517`), and it runs
  *synchronously inside* the Zustand updater (`state/content-store.ts:1597`, inside
  `commitWorkspace` at `:1576-1600`) — so it completes before React re-renders.
- **The collapse branch is not lossy.** `closeContentTab`'s early return
  (`state/content-store.ts:2266`) looked like it might skip `selectedContentId` /
  `openContentIds`, but `collapseForOccupancy` returns all three
  (`state/content-store.ts:1230-1234`), and `resolveLayoutForOccupancy` bails out entirely
  in `single` mode (`state/content-store.ts:1156`) — the layout in the screenshot.

**Hypothesis** (not confirmed — see **Blocked on**). Something re-opens the tab immediately
after the close commits. Two candidate paths, in order of suspicion:

1. **An open intent overwrites the close intent.** `closeContentTab` records
   `rememberIntent(contentId, "close")` (`state/content-store.ts:2188`), which is what stops
   a stale server snapshot from resurrecting the tab — the reconcile filters on it at
   `state/content-store.ts:2450-2459` and `:2504-2508`. But `rememberIntent` is
   *last-write-wins by design*: "Recording the opposite intent replaces the previous one"
   (`state/content-store.ts:650-652`). And closing the **last** tab drives
   `openContentIds.length` to 0, which re-fires the URL-restore effect in
   `components/content/MainPanelWorkspace.tsx:280-377` (deps at `:377`) — whose first act is
   `markLocalOpenIntents(...)` (`:342`), i.e. `rememberIntent(..., "open")`
   (`state/content-store.ts:716-719`). If that effect finds anything to restore, it converts
   the just-recorded close into an open and the next poll legitimately re-adds the tab.
   I could not close this loop by reading alone: on the paths I traced the URL params are
   already cleared by then, so the effect *should* find nothing. The reason it stays the lead
   candidate is that it is the one mechanism that fires **only when the last tab closes**,
   which matches a single-tab screenshot.
2. **A reconcile landing in the write window.** The debounced workspace write races the
   poll; the intent system exists for exactly this and is the thing to instrument first.

**Approach.** Re-verify on current `main` before writing any fix — see **Blocked on**. If it
still reproduces, instrument rather than guess: the repo already ships a flag-gated tracer
for this loop (`lib/core/workspace-trace.ts`, added in `4b58566`, and `closeContentTab` is
already in its action list at `lib/core/workspace-trace.ts:60`). Turn it on, close the last
tab with the shortcut, and read whether the tab returns via a `url:restore` or via a
reconcile — that single trace line picks between the two hypotheses and tells you which fix
to write.

If it is path 1, the fix is to stop the restore effect from laundering a close into an open:
skip `markLocalOpenIntents` for a content id whose current intent is `"close"`, or have the
effect ignore a restore triggered by a close in the same tick. If it is path 2, the intent
backstop or the write/poll ordering is the target.

Rejected: *special-casing the shortcut* — it shares the reducer with the X button, so a
shortcut-only fix would leave the same bug reachable by clicking X on the last tab, and would
be papering over whichever re-open path is real. Also rejected: *suppressing the restore
effect whenever `openContentIds` empties* — that effect is load-bearing for deep links and
cold starts, and disabling it would reintroduce the "flashes then disappears" regression that
`state/content-store.ts:709-714` documents by name (the effect's own note at
`components/content/MainPanelWorkspace.tsx:332-334` points at it).

**Gates.** `typecheck` → `lint` → `build`. There is a dedicated harness for this subsystem —
`scripts/workspace-pane-placement-smoke.ts` already pins close/collapse/intent cases
(`confirmWorkspaceWrite` at `:247`, `:413`, close sequences at `:639-686`) — so add the
regression case there rather than only testing by hand. Browser smoke is mandatory: this is
a timing bug and no type check will see it.

```markdown
- [ ] **Smoke #223:** with one tab open, press Cmd+Alt+W → the tab leaves the rail and stays gone (no skeleton, no reappearance after ~10s of polling)
```

**Blocked on.** Nothing blocks *planning* this, but the first action is re-verification, not
a fix, and the plan is deliberately hedged for one reason: **~24 commits have landed over
this exact code since the 2026-09-12 report**, several of them squarely on this mechanism —
`304c12e` (2026-10-03) *"one state write in flight; a 409 reconciles instead of re-opening"*,
`9fd08ac` (2026-10-02) *"a dragged tab stays where it was dropped across a stale poll"*, and
`0c78e6b` (2026-10-06) *"a pane folds only when THIS removal emptied it"*. `304c12e` in
particular is a fix for "something re-opens a tab after a state write", which is this bug's
shape. It may already be fixed.

It is **not** filed under "Likely already fixed" because none of those commits names #223 and
none of them touches the shortcut handler, which is unchanged since `8809a16` (2026-09-02) —
ten days *before* the report. So the evidence points at "possibly fixed by a neighbour", which
is an impression, not the named cause that table requires.

The specific observation reading the code cannot supply: **which code path re-adds the tab.**
The rail proves it is re-created, but the re-creation happens in a poll/debounce race whose
ordering is not determined by the source — it depends on whether the debounced write or the
next poll wins, which is wall-clock, not control flow. The tracer above is what resolves it,
and it needs a running app.

## #70 — Dramatic unblurred and ungraceful Mermaid editing

**Reported:** 2026-06-13 · **Labels:** `bug`, `Visualizations`

**Symptom.** Every keystroke while editing a Mermaid diagram raises a noisy syntax error,
reported as "3 repeating" errors. The error block is large and eats the available space in
the embed, viewer and toaster surfaces.

**Where it lives.** One component, one effect:
`components/content/viewer/MermaidViewer.tsx:223-271`. It pre-validates with
`mermaid.parse(source)` and renders, and its catch block raises **exactly three
user-visible error surfaces** for a single failure:

1. `toast.error("Mermaid Syntax Error", { duration: 5000 })` —
   `components/content/viewer/MermaidViewer.tsx:252-255`
2. a large red block injected into the preview container via `innerHTML` —
   `components/content/viewer/MermaidViewer.tsx:257-268`
3. a `renderError` banner in the JSX — set at
   `components/content/viewer/MermaidViewer.tsx:249`, rendered at `:542-544`

**Diagnosis.** Confirmed against the code, and it matches the report line for line. Two
independent faults compound:

- **No debounce on render.** The effect's dep array is
  `[source, mermaidReady, isEditMode, resolvedTheme]`
  (`components/content/viewer/MermaidViewer.tsx:271`), so it re-parses on *every* source
  change — i.e. every keystroke. Mid-edit text is invalid by definition, so the error path
  fires continuously. Note the contrast: *saving* is already debounced 2s
  (`components/content/viewer/MermaidViewer.tsx:110-135`); rendering never was.
- **Three surfaces for one error.** "See 3 Mermaid errors" is not an exaggeration or a
  mermaid-internal repeat — it is these three code paths, all unconditional in the same
  `catch`.

The owner's ask maps cleanly onto both: *"blur temporary changes for at least 3 seconds"* is
the debounce, and *"only using toaster or one compact inline error surface"* is collapsing
the three.

**Approach.** In `MermaidViewer.tsx`:

1. **Debounce the render** ~750ms–1s while `isEditMode`, and keep the last successfully
   rendered SVG on screen (blurred/dimmed) instead of destroying it — the effect currently
   clears the container at `:235` before it knows whether the new source parses. Render
   immediately on mount, on theme change and on edit-mode exit; only typing is debounced.
   The issue says 3s; 3s of staleness while typing feels broken, so I would ship ~1s and let
   the owner tune it — flagging the deviation rather than silently picking a different number.
2. **Keep one error surface.** Keep the compact inline `renderError` banner (`:542-544`),
   drop the injected `innerHTML` block (`:257-268`) and drop the per-render `toast.error`
   (`:252-255`). The toast is the worst of the three while typing: it is transient, stacks,
   and 5s outlives the keystroke that caused it. Keep `clientLogger.warn` (`:244-248`) —
   it is not user-visible.
3. **While debouncing, suppress the error entirely** until the user pauses. An error shown
   mid-word is noise, not information.

This fixes all three reported surfaces at once because `FullscreenMermaidViewer` wraps this
same component (`components/content/viewer/FullscreenMermaidViewer.tsx:10`) and the note-embed
path is the same component behind its `isEmbedded` prop — there is no second render/error
implementation to keep in sync.

Rejected: *suppressing mermaid's own error rendering only* — the three surfaces are ours, not
mermaid's, so that would change nothing. Rejected: *moving all errors to the toast* — the
owner offered it as an option, but a toast is the wrong home for a persistent state ("your
diagram does not parse"), and it is exactly what makes typing noisy today.

**Gates.** `typecheck` → `lint` → `build`. No schema, no new TipTap node, no new publishing
block, so no static gate beyond the standard three. Dark mode: the inline banner being kept
already carries `.dark` companions (`:261-263`); if you restyle it, keep them.

```markdown
- [ ] **Smoke #70:** in a Mermaid diagram, type an invalid line character-by-character → the last valid diagram stays visible (dimmed), no toast fires, and one compact inline error appears only after you stop typing
```

**Note while you are in this file** (not part of this bug, do not widen the PR): `errorMessage`
is interpolated into `innerHTML` unescaped at
`components/content/viewer/MermaidViewer.tsx:257-268`, and mermaid error text echoes the
user's own source. Deleting that block per step 2 removes the sink as a side effect, which is
the tidiest outcome. If you keep it for any reason, escape it or build the node with
`textContent`.

## #184 — Darkmode contrast issues (ongoing homework)

**Reported:** 2026-08-27 · **Labels:** `bug`

**Symptom.** Standing umbrella issue for dark-mode contrast gaps. One unchecked item:
*"Folder affordances, including various folder views"*, with two screenshots of folder views.
The owner's constraint: match the existing design system rather than invent new colours, and
meet existing contrast standards.

**Where it lives.** `components/content/folder-views/` — and the cause is a single repeated
mistake, not scattered bad colours.

The folder views build their surfaces from the design system but take only **part** of each
token. `getSurfaceStyles` returns four CSS-variable references, border included
(`lib/design/system/surfaces.ts:69-76`), and its own docstring says the browser resolves them
per theme via the `.dark` cascade (`lib/design/system/surfaces.ts:64-66`). The generated
variables are already correct in **both** themes:

- `app/globals.css:288` — `:root` → `--surface-glass-0-border: 1px solid rgba(15, 23, 42, 0.08)` (dark slate, for light mode)
- `app/globals.css:367` — `.dark` → `--surface-glass-0-border: 1px solid rgba(255, 255, 255, 0.10)` (white, for dark mode)

But every folder view applies `background` and `backdropFilter` from the token and then writes
the border as a **hardcoded Tailwind class** — `border-white/10` — which is the dark-mode value
frozen into both themes. Same for hover affordances (`hover:bg-white/5`, `/20`, `/50`).

Eleven call sites across five files:

| File | Lines |
|---|---|
| `components/content/folder-views/ListView.tsx` | `168` (`border-white/10 hover:bg-white/5`, beside `glass0` at `:174-177`) |
| `components/content/folder-views/DashboardView.tsx` | `241`, `248`, `262` |
| `components/content/folder-views/GalleryView.tsx` | `205`, `231` |
| `components/content/folder-views/KanbanView.tsx` | `105`, `122`, `422`, `451` |
| `components/content/folder-views/CanvasView.tsx` | `124` |

In light mode a white border at 10% over a light glass surface is invisible, so rows and cards
lose their boundary, and a `hover:bg-white/5` hover is a no-op — which is the "folder
affordances" complaint exactly.

**Diagnosis.** Confirmed. Note the shape of the evidence: text colours in these same files
*already* carry `dark:` companions (e.g. `text-gray-900 dark:text-gray-100` at
`DashboardView.tsx:251`), because `627427f` (2026-09-15) *"fix(ui): dark text on themed
surfaces declares a dark-mode colour"* swept the **text**. Borders and hover states were not
in that sweep. So this is the unfinished half of a fix that already landed, which is why the
remaining item is still live.

**Approach.** Replace the hardcoded border/hover classes with the design-system token the
component is already using — this is the owner's "modify the existing design system" rather
than new colours, and it is a smaller diff than adding eleven `dark:` variants:

1. Where the component already spreads `glass0` into `style`, add `border: glass0.border`
   (the token is right there and already theme-aware) and drop `border-white/10`.
2. For hover affordances, which have no token today, add one `--surface-*-hover` variable
   defined under both `:root` and `.dark` in the generated token set (`lib/design/system/`,
   regenerated with `pnpm build:tokens`) rather than hand-writing `dark:` pairs at eleven
   sites. One token, eleven consumers.

**Three sites that look like hits and must be left alone** — check these before any
find-and-replace:

- `components/content/folder-views/KanbanView.tsx:479-480` — `bg-white` + `text-gray-900` on
  the drag-overlay card. **Deliberate**, with a comment saying so at `:476-478`: an opaque
  white card reads as "lifted" over any background, so the dark text is correct and wants no
  `dark:` companion.
- `components/content/folder-views/GalleryView.tsx:253`, `:272` — `text-white/80` over media
  thumbnails. Correct in both themes; it sits over imagery, not over a themed surface.
- `components/content/folder-views/MediaLightbox.tsx:205` — `text-white/60` on the lightbox's
  own dark backdrop. Correct in both themes.

Rejected: *adding `dark:` variants at each site* — it works, but it leaves the token unused
and the next folder view will repeat the mistake. Rejected: *changing the `rgba(255,…)` values
in `lib/design/system/surfaces.ts:24-57`* — those are the dark-theme source values and are
already correct; the generated `:root`/`.dark` split proves the token layer is fine. The bug is
that the components bypass it.

**Gates.** `typecheck` → `lint` → `build`, plus `pnpm build:tokens` if you add the hover token
(the generated `app/globals.css` block is committed, so regenerate and commit it together).
`pnpm publishing:audit:themes` does **not** cover this — it audits `.public-prose .block-*`
rules on the publishing surface, not app components — so the verification here is visual.
Exercise every folder view in **both** themes: List, Dashboard, Gallery, Kanban, Canvas.
