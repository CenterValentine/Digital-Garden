## #223 — Shortkey for closing a tab doesn't fully close out a tab

**Reported:** 2026-09-12 · **Labels:** `bug`

**Symptom.** The close-tab chord clears the content area to a loading skeleton, but the tab
stays in the header rail with its title intact ("Sept 11, 2026" in your screenshot). Expected:
the tab disappears and the pane falls back to the previously viewed tab.

**Where it lives.**

- The chord is bound in `components/content/headers/MainPanelHeader.tsx:654-684`. It accepts
  `Cmd/Ctrl+Alt+W` and `Cmd+Ctrl+W`, and on a match calls
  `closeContentTab(pane.activeTabId)` (`:679`).
- The X button on a tab calls the **same** action with a different id:
  `closeContentTab(tab.id)` (`:890`), where `tab` comes from `visibleTabs`.
- The action itself is `state/content-store.ts:1724-1806`. Tab ids are derived
  deterministically from the content id (`getTabId`, `:202-204` → `tab:<contentId>`), so
  there is never a second tab for the same content to be confused with.
- The rail renders `visibleTabs`, which is `pane.tabIds` **after** the workspace tab-type
  filter (`MainPanelHeader.tsx:426-435`). The filter is view-only by design —
  `state/workspace-tab-filter-store.ts:9-27` and the comment at `MainPanelHeader.tsx:426`
  both say hidden tabs stay open and *active content stays put*.

**Hypothesis** (not confirmed against a running app — see the uncertainty below). The chord
and the X button call identical code with identical semantics, so the divergence cannot be
inside `closeContentTab`; it has to be in **which id the chord passes**. Two mechanisms
produce exactly the reported picture, and they are distinguishable in a few seconds of
devtools:

1. **`pane.activeTabId` is not always the tab that looks active.** A tab hidden by the
   tab-type filter remains `pane.activeTabId` — that is the store's stated contract. The
   chord then closes the *hidden* tab: the content area re-resolves to whatever
   `closeContentTab` picks next (skeleton while it loads), while the rail, which only ever
   rendered the visible tabs, is unchanged. The user sees "content cleared, tab stayed".
2. **A late open-intent re-creates the tab.** `rememberIntent(contentId, "close")` at
   `content-store.ts:1729` is what stops a workspace reconcile from re-adding a closed tab,
   but `setSelectedContentId` records the opposite intent and explicitly overrides it
   (`:1316`, and `rememberIntent` at `:482-490`). Anything that selects the just-closed
   content right after the close — and the chord deliberately fires while the editor for
   that note is focused and mid-autosave (`MainPanelHeader.tsx:660-661`) — re-creates
   `tab:<contentId>` with its title restored from `contentMeta` and its payload refetching,
   which is literally a tab with a skeleton behind it.

**Separately live, and not a hypothesis:** the issue's expected behaviour asks for "the next
available tab (typically the last viewed active tab)". The successor is chosen
**positionally** — `pane.tabIds[removedIndex] ?? pane.tabIds[removedIndex - 1] ?? null`
(`content-store.ts:1742-1746`, and again for each layout snapshot at `:1765-1770`). That is
the right-hand neighbour, not the last viewed tab. Recency is already available:
`state/tab-activity-store.ts:9-19` documents that `navigation-history-store` stamps every
pane navigation with a timestamp and persists it.

**Approach.**

1. First, settle which mechanism it is, because the fixes do not overlap: open devtools,
   fire the chord, and check whether `useContentStore.getState().tabs["tab:<id>"]` is gone
   (mechanism 1) or reappears a tick later (mechanism 2).
2. **If mechanism 1:** make the chord target what the user can see. The cheapest correct
   version resolves the id in the component — close `pane.activeTabId` only when it survives
   the same `isTabGroupVisible` test the rail applies, else the active *visible* tab. Better,
   and still small: stop letting the filter hide the active tab at all — when a filter would
   hide `pane.activeTabId`, re-point it at the nearest visible tab, so the store's notion of
   "active" and the rail's can never disagree. Rejected: dropping the filter's "active
   content stays put" contract wholesale — it is a deliberate decision with a written
   rationale, and changing it would move content under the user on a filter click.
3. **If mechanism 2:** the close intent must win over a selection of the content being
   closed. Give `rememberIntent` a short grace window in which a `"close"` is not overridden
   by an `"open"` for the same content id, and find the caller (editor unmount, autosave
   completion, or the URL sync) with a one-line log at `:1316`. Rejected: suppressing the
   chord while the editor is focused — the comment at `:660-661` is right that the tab you
   want to close is usually the one you are editing.
4. **Either way**, fix the successor choice: pick the surviving tab in the pane with the most
   recent navigation-history stamp, falling back to the positional neighbour when no stamp
   exists (a restored tab never clicked). Keep it in `closeContentTab` so the X button and the
   chord inherit it together.

**Gates.** `pnpm typecheck` → `pnpm lint` (the store and the header are both React-Compiler
sensitive; a new dep on the filter store in that effect must be declared, not suppressed) →
`pnpm build`. No schema change, no TipTap node, so no migration and no Hocuspocus redeploy.

```markdown
- [ ] **Smoke #223:** open three tabs, visit the first, then the third, then press the close-tab chord on the third → the third tab disappears from the rail and the first tab's content is shown (not a skeleton, not the second tab)
- [ ] **Smoke #223 (filtered):** with a tab-type filter active that hides the current tab, press the chord → the visibly active tab is the one that closes
```

## #184 — Darkmode contrast issues (ongoing homework)

**Reported:** 2026-08-27 · **Labels:** `bug`

**Symptom.** Dark mode has unpaired light-mode colours left over across the app. The issue
carries one itemized request: "Folder affordances, including various folder views."

**That one item has shipped.** `627427f` (2026-09-15, PR #239) paired 61 dark-text sites
across all five folder views and every content-type viewer, and added a gate so it cannot
regress. Its commit message names exactly the surfaces in your screenshots — the folder
title, the Kanban column headers, every card title. The issue says it should never be closed
until dark mode is fully squashed, so it stays open; but the concrete checkbox in it is done,
and this week's plan is therefore about the *next* slice rather than that one.

**Where it lives.**

- The gate is `scripts/validate-dark-contrast.ts`, wired into `build` via
  `contrast:check` (`package.json:14`, `:75`).
- Its scope is two directories — `SCAN` at `:27-30`: `components/content/folder-views` and
  `components/content/viewer`. Everything else in the app is unchecked.
- It only matches **text** shades: `DARK_TEXT` at `:31` covers
  `text-{gray,neutral,slate,zinc,stone}-{500..900}`. Backgrounds and borders
  (`bg-white`, `border-gray-200`) are outside the invariant.
- Widening `SCAN` to the adjacent themed content surfaces flags **5 sites** today:
  `components/content/file-tree/RootNodeHeader.tsx:149`,
  `components/content/context-menu/ContextMenu.tsx:235`, and
  `components/content/toolbar/ToolDebugPanel.tsx:41,60,67`. `components/content/headers`
  and `components/content/data` are already clean.

**Diagnosis.** The class of defect is settled and documented: Tailwind's gray scale does not
adapt, so an unpaired dark shade on a themed glass/slate surface renders black-on-dark, and
it is invisible to typecheck, to lint, and to anyone developing in light mode. The only thing
that keeps it fixed is the gate, and the gate currently sees two directories out of the
content shell.

**Approach.** Widen the invariant one ring outward rather than hunting screenshots: add
`components/content/file-tree`, `components/content/headers`, `components/content/context-menu`
and `components/content/toolbar` to `SCAN`, then pair the five sites it flags (or mark a
surface with the existing `"Deliberately light in BOTH themes"` escape hatch, as the Kanban
drag preview does). Prefer the design-system tokens over new literal colours — the issue asks
for that explicitly ("We try at all costs to modify the existing design system").

Rejected: **the `people` dialogs** (23 unpaired sites, mostly
`components/content/people/PeopleMountPickerDialog.tsx`). PR #239 deliberately put
light-in-both-themes dialogs out of scope as "internally consistent — a separate question
from contrast, and a bigger change", and that call still stands. Worth one note for later
though: `PeopleMountPickerDialog.tsx:534` already carries `dark:hover:bg-white/[0.04]` on a
`bg-white` card, so that dialog is *half* converted — a white hover on a white card is
invisible. It is a real defect, but a different one from this issue, and it needs your call
on whether that dialog becomes themed.

Rejected: extending the gate to backgrounds and borders in the same sitting. The text
invariant is mechanical ("pair it"); a background invariant needs a surface-by-surface
decision about what the dark equivalent *is*, which is design work, not a gate.

**Gates.** `pnpm contrast:check` (must fail before the fix and pass after — that is the
proof) → `pnpm typecheck` → `pnpm lint` → `pnpm build`. The two Playwright light/dark
projects already snapshot the signed-out surfaces; none of the five sites is on one, so no
snapshot churn is expected — if `pnpm test:e2e` does diff, the PNG is the contract and
wants reviewing before it is regenerated.

```markdown
- [ ] **Smoke #184:** in dark mode, open the file tree root header, right-click a tree node, and open the tool debug panel → every label reads light-on-dark with no black-on-dark text
```

**Blocked on.** Nothing for the slice above. But the *issue* cannot be finished, only
advanced: beyond these five sites it names no surface, and picking the next one is your
call — a screenshot or a new checkbox in the issue body is what unblocks the slice after
this one. See the note at the bottom about this issue never being closeable by
`/pr-closeout`.

## #70 — Dramatic unblurred and ungraceful Mermaid editing

**Reported:** 2026-06-13 · **Labels:** `bug`, `Visualizations`

**Symptom.** Every keystroke in a Mermaid diagram that leaves the source temporarily invalid
raises a long, noisy format error — three error surfaces at once — and the rendered diagram
is replaced by a red panel. Asked for: temporary changes stay blurred for ~3 seconds, and
one compact error surface instead of three.

**Where it lives.** One file, used by all three entry points.
`components/content/viewer/MermaidViewer.tsx` is mounted by the standalone visualization
viewer, by `FullscreenMermaidViewer.tsx:67` (a thin wrapper), and by the note embed —
`lib/domain/editor/extensions/blocks/mermaid-block.ts:463-479` dynamically imports the same
component. So this is one fix, not three.

The render effect is `MermaidViewer.tsx:223-271`:

- it depends on `source` directly (`:271`), and `source` updates on **every keystroke** via
  `handleSourceChange` (`:186-211`) — the only debounce in the file is on *saving*
  (`debouncedSave`, `:110-141`), not on rendering;
- on failure it fires `toast.error("Mermaid Syntax Error")` with `duration: 5000` and **no
  toast id** (`:251-255`), so rapid typing stacks a fresh 5-second toast per failed
  keystroke — this is the "3 repeating errors";
- it then overwrites the preview with a large inline red panel (`:257-266`), destroying the
  last good SVG;
- and `renderError` renders a *third* copy of the same message as a strip under the textarea
  in edit mode (`:542-546`);
- plus a `clientLogger.warn` per keystroke (`:241-247`).

That is exactly the issue's "takes up available space in the embed in editor, view and
toaster surfaces".

**Diagnosis.** Confirmed in the source. Two independent defects: the render path is not
debounced, and a failed render has three reporting surfaces where the owner asked for one.
The lost-diagram part is the `catch` block replacing `previewRef.innerHTML`, not the
`innerHTML = ""` clear at `:235` — `parse` throws before that line is reached.

**Approach.**

1. **Debounce the render, keep the last good diagram.** Drive the effect off a debounced
   mirror of `source` (~600–800 ms idle) instead of `source` itself, and hold the last
   successful SVG in a ref. While the source is dirty or invalid, leave that SVG mounted
   under a `blur-sm opacity-60` wrapper rather than wiping it — that is the owner's
   "blur temporary changes" requirement, and it also means an in-progress edit never costs
   you the picture you were editing. Keep the first render eager so an empty diagram still
   renders immediately.
2. **One error surface, chosen by mode.** In edit mode the compact strip under the textarea
   (`:542-546`) is the right one: it is adjacent to the source, it is small, and it does not
   consume the preview. Drop the injected red panel entirely, and drop the toast in edit mode.
   In read mode there is no strip, so keep the toast there — but give it a stable
   `id` (e.g. `` `mermaid-error:${contentId}` ``) so sonner replaces rather than stacks it.
3. **Log once per distinct error**, not once per keystroke — compare against the last logged
   message before calling `clientLogger.warn`.

Rejected: mermaid's own `suppressErrorRendering` config. It only suppresses mermaid's error
*icon* (which this code already avoids by catching and rendering its own panel); it does
nothing about the stacked toasts or the destroyed good render, which are the actual
complaint.

Rejected: validating only on blur. The split view's whole point is a live preview; the owner
asked for it to be calm, not for it to stop updating.

**Gates.** `pnpm typecheck` → `pnpm lint` → `pnpm build`. Two gates in `build` are
specifically relevant: `contrast:check` (any new dark text class in this file needs a `dark:`
companion, and this file is inside its scanned `components/content/viewer`) and
`collab:schema:check` (unchanged here — the fix touches no TipTap node, so **no Hocuspocus
redeploy** is needed). The mermaid block has committed Playwright baselines —
`tests/e2e/__snapshots__/editor/per-block.spec.ts/editor-mermaid-block-{light,dark}.png` —
so run `pnpm test:e2e` and expect the embed's chrome to be unchanged; a diff there means the
blur wrapper leaked into the collapsed/expanded resting state.

```markdown
- [ ] **Smoke #70:** open a Mermaid diagram, type a line of invalid syntax one character at a time → the last good diagram stays visible and blurred, exactly one error surface appears (the strip under the textarea), and no toast stacks up; finishing the valid line restores the sharp diagram
```
