## #319 — Editor jumps to top when collaboration sleeps or wakes — provider demotion recreates the TipTap editor

**Reported:** 2026-11-18 · **Labels:** `bug`, `Content Note`, `hocuspocus`, `collaboration`

**Symptom.** While scrolled partway down a note, the view snaps back to the top of the
document and the caret/selection is lost. The jump coincides with the collaboration
signal in the note header changing between active and dormant. Found in the Electron M0
smoke, but the mechanism is in the web app — two windows on one note only made it easy to
trigger.

**Where it lives.** The recreate trigger is confirmed exactly where the issue says it is:

- `components/content/editor/MarkdownEditor.tsx:486-492` — `editorMode` is derived from
  **provider presence**: `collaborationState.provider ? "collaboration" : "collaboration-local"`.
- `components/content/editor/MarkdownEditor.tsx:1022` — `editorMode` is a `useEditor` dep
  (`}, [editorMode, collaborationDocument]);`). A flip destroys and rebuilds the editor.
- `lib/domain/editor/extensions-client.ts:195-226` — this is *why* the recreate is
  structural rather than incidental: `CollaborationCaret.configure({ provider })` is
  spread into the extension list **only when a provider exists**, so provider presence
  changes the extension set itself, not just an option.
- `lib/domain/collaboration/runtime.ts:2833-2837` — `destroyProviderOnly()` nulls
  `entry.hocuspocusProvider`, which is what flips `editorMode`.

The call path that reaches `destroyProviderOnly` with a note open:

- `lib/domain/collaboration/runtime.ts:2708-2746` — `maybeEnterSleepMode()` (visibility
  timer `VISIBILITY_SLEEP_DELAY_MS` = 3 min, inactivity timer
  `INACTIVITY_SLEEP_DELAY_MS` = 10 min; constants at `:437-438`) calls
  `destroyProviderOnly(entry)` at `:2735` after a `COOLDOWN_MS` grace (`:431`, 120 s).
  It guards on `localDirty`, `unsyncedUpdateCount`, `networkState` and
  `liveConsumerCount > 0` — but **not** on `consumerCount`.
- `lib/domain/collaboration/runtime.ts:1984-1986` — `liveConsumerCount` counts only
  consumers with `requiresLiveTransport`, and the main pane registers itself with
  `requiresLiveTransport: false` (`components/content/content/MainPanelContent.tsx:642-655`).
  So an ordinary open note contributes **0** to `liveConsumerCount` and does not block sleep.
- Waking again (presence promote, or a second window joining) re-creates the provider and
  recreates the editor a second time.
- `components/content/headers/MainPanelHeader.tsx:58-61` — `ACTIVE_TRANSPORT_STATES`
  changes on the same transitions, which is the observed correlation.

**Correction to the issue's repro list.** Step 1 ("stay solo and synced for ~2 min →
cooldown → provider demoted") should not fire with the note open.
`maybeStartCooldown` (`lib/domain/collaboration/runtime.ts:2679-2702`) only demotes when
`canDemoteProvider(entry)` is true, and that requires
`consumerCount === 0 && liveConsumerCount === 0`
(`lib/domain/collaboration/runtime.ts:2766-2777`) — a mounted editor is a consumer.
Plan around steps 2 (sleep on hidden/idle, then promote on return) and 3 (second
window/tab → promote). If step 1 *does* reproduce for you with the note in front of you,
that is a second, separate defect in the consumer accounting and worth its own issue.

**Diagnosis.** Two defects, one trigger.

1. **Nothing restores the offset.** `editorScrollRef`'s div
   (`components/content/editor/MarkdownEditor.tsx:1753-1754`, `relative flex-1 overflow-y-auto`)
   stays mounted across the recreate; only the ProseMirror DOM inside
   `<EditorContent editor={editor} />` (`:1943`) is swapped. While it is empty the
   container's content height collapses, the browser clamps `scrollTop` to 0, and then the
   new view mounts at the top. The viewport-memory restore that would fix this does not
   run: `useViewportMemory`'s restore effect is keyed `[contentId, region, enabled]`
   (`lib/domain/content/use-viewport-memory.ts:78-147`), and `contentId` has not changed —
   only the editor instance has. The hook is called at
   `components/content/editor/MarkdownEditor.tsx:1164`. Its own comment at
   `use-viewport-memory.ts:89-93` anticipates "a collaborative note's Y.Doc materializes
   after the editor is recreated" — but only for a recreate that accompanies a contentId
   change.

2. **The collapse poisons the remembered offset.** The clamp to 0 fires a real `scroll`
   event, the capture-phase listener records it unguarded
   (`lib/domain/content/use-viewport-memory.ts:61-69`, `suppressRef` is false because no
   restore is pending), and `recordViewport` does not filter 0
   (`lib/domain/content/viewport-memory.ts:130-147`). So `0` is written to
   `workspaceTabViewports` under this note's `note` region — meaning the *next* tab switch
   back also lands at the top. That is #64's symptom, re-created from a different trigger
   on content whose stored offset has been overwritten.

No content is at risk: the Y.Doc survives the recreate (`collaborationDocument` is
unchanged), so this is lost position and lost caret, not lost text. Hence P3 rather than P0.

**Approach.** Fix the symptom properly at the viewport-memory seam; do **not** take the
provider out of the dep array this week.

Add an optional `restoreKey` (or `remountToken`) to `useViewportMemory`'s options, include
it in the restore effect's dep array (`lib/domain/content/use-viewport-memory.ts:147`), and
have `MarkdownEditor` pass the editor instance from `useEditor`. One change then buys both
halves: the effect re-runs when the editor is rebuilt and restores the saved offset, and
its existing `suppressRef` gate (`:86`) blocks the poison `0` write for the duration of the
restore. Default the option to `undefined` so `MainPanelContent:2709` and
`ExpandableEditor:107` are untouched.

- **Named uncertainty (settle this first, it is a one-minute browser check).** The
  suppression only helps if `suppressRef` is set *before* the clamp's `scroll` event is
  dispatched. Effect ordering versus scroll-event dispatch is not guaranteed by spec. If
  the `0` still lands, the fallback is a one-line guard in `handleScroll`: ignore a
  recorded `0` when the scroller's `scrollHeight - clientHeight <= 1` (nothing to scroll
  yet means the content is mid-swap, not that the reader went to the top). Prefer the
  suppression if it holds; it needs no new rule.
- **Rejected — snapshot and restore inside `MarkdownEditor` with its own ref.** It
  duplicates the hook's job and puts two writers on one `(contentId, region)` key, which
  the comment at `MarkdownEditor.tsx:1156-1163` deliberately avoids (that is exactly why
  the hook is on the outer wrapper and `editorScrollRef` kept its single job).
- **Rejected for this week — stop recreating on provider presence** (the issue's fix
  direction 2). It is the right end state, and it is the only option that also saves the
  **caret**, which a scroll restore does not. But `CollaborationCaret` binds awareness from
  the provider at configure time (`lib/domain/editor/extensions-client.ts:201-224`) and
  TipTap offers no re-point API, so this needs a wrapper extension owning its own awareness
  binding — a larger change than a week's plan, and one that must keep the
  `collaborationDocument` dep intact (the 2026-10-06 wrong-Y.Doc report; see
  `docs/notes-feature/core/CONTENT-LOAD-CASCADE.md` §9.4 and the deps comment at
  `MarkdownEditor.tsx:999-1021`). Worth its own issue.
- **Rejected as the fix, worth a decision — don't sleep a note that is open** (fix
  direction 3). Adding `if (entry.state.consumerCount > 0) return;` to `maybeEnterSleepMode`
  is a one-liner, but it holds a WebSocket open for every open-but-idle note, which is the
  cost the sleep machinery exists to avoid (presence cadence, Cloud Run). A narrower variant
  — skip sleep only while the document is **visible in a focused window** — is defensible
  and cheap; it is a product/cost call, so it is yours, not the fixer's.
