## #184 — Darkmode contrast issues (ongoing homework)

**Reported:** 2026-08-27 · **Labels:** `bug`

> **This issue is deliberately never-closing.** The body states it "should never be closed
> until darkmode contrast issues are fully squashed", and it carries a checklist of
> surfaces rather than a single defect. That has a direct consequence for the fixing PR —
> see **Gates** below, where the smoke line is written *without* a `**Smoke #184:**`
> marker on purpose.

**Symptom.** Dark mode reaches most of the app but leaves gaps. The one checklist item
filled in so far, with two screenshots, is "Folder affordances, including various folder
views" — text and chrome in the folder viewer that do not meet contrast against the dark
surface.

**Where it lives.** The folder surfaces were authored *dark-first* — they use the glass
utilities `bg-white/5` and `border-white/10` for chrome — but their text colours were left
as fixed light-mode greys with no `dark:` companion. The two families fight each other, so
these components are actually wrong in *both* themes.

The affordance in the screenshots (folder header + view switcher):

- `components/content/viewer/FolderViewer.tsx:121` — folder icon, `text-gray-600`
- `:122` — the folder title, `text-gray-900`; near-invisible on the dark surface
- `:126` — the switcher shell, `border-white/10 bg-white/5`; dark-first, so it nearly
  disappears in *light* mode
- `:134` — inactive switcher buttons, `text-gray-400 hover:text-white`; the hover state is
  white-on-light in light mode

The views themselves, same pattern — counted occurrences of fixed greys / `bg-white` with
no `dark:` companion:

| File | Count | Worst offenders |
|---|---|---|
| `components/content/folder-views/KanbanView.tsx` | 11 | `:114`, `:423`, `:477` card and column titles `text-gray-900`; `:476` `bg-white` drag preview |
| `components/content/folder-views/DashboardView.tsx` | 9 | `:251` card title `text-gray-900`; `:248` `bg-white/5` header strip |
| `components/content/folder-views/ListView.tsx` | 6 | `:182` row title `text-gray-900`; `:167` `border-white/10 hover:bg-white/5` row |
| `components/content/folder-views/CanvasView.tsx` | 5 | `:112`, `:127` extension label and icon `text-gray-600` |
| `components/content/folder-views/GalleryView.tsx` | 2 | `:184`, `:193` loading / empty copy `text-gray-600` |

`FolderViewContainer.tsx` and `MediaLightbox.tsx` are already clean.

**Diagnosis.** Confirmed against the files, not inferred. The repo already has the
theme-aware convention these should be using — `text-foreground` (78 uses) and
`text-muted-foreground` (197 uses) across `components/content/` — and the folder surfaces
simply never got converted. Item titles rendered `text-gray-900` on a dark glass panel are
the exact failure the screenshots show.

**Approach.** Convert the fixed colours to the semantic tokens the rest of
`components/content/` already uses, rather than bolting a `dark:` variant onto each grey:

- `text-gray-900` → `text-foreground`
- `text-gray-600` / `text-gray-700` → `text-muted-foreground`
- `bg-white` (Kanban drag preview, `:476`) → the surface token used by sibling cards
- the dark-first glass (`bg-white/5`, `border-white/10`, `hover:text-white`) → the
  equivalent Liquid Glass surface from `lib/design/system/` so it holds in both themes

Two alternatives considered and rejected:

- **Add `dark:` companions to each existing grey.** Doubles the class list, leaves the
  codebase with two competing conventions in one directory, and does nothing for the
  dark-first glass that is wrong in light mode. The tokens fix both directions at once.
- **Fix only what the screenshots show (`FolderViewer.tsx`).** Cheaper, but the reporter
  framed the checklist item as "folder affordances, *including various folder views*", and
  the same five files would come back next week. The whole directory is ~33 occurrences —
  not meaningfully more work than the header alone.

Keep the slice to these six files. This issue invites scope creep by design; resist widening
into other surfaces in the same PR, and tick only the folder-affordances checklist item.

**Gates.** `pnpm typecheck` → `pnpm lint` (the `--max-warnings 175` ratchet; a pure class
swap should not move it) → `pnpm build`.

No automated gate covers this. `pnpm publishing:audit:themes` only scans
`.public-prose .block-*` CSS rules and will not see Tailwind classes in these components,
and the Playwright dark-mode suite cannot reach a folder route — `tests/e2e/dark-mode/
authenticated-routes.spec.ts` is still `test.skip` pending the auth fixture. Verification is
manual, in both themes.

Verification line for the PR's Pre-merge checklist — **note the deliberately absent
`Smoke #184:` marker**:

```markdown
- [ ] Dark-mode folder pass: open a folder in dark mode, switch through List / Dashboard /
      Kanban / Canvas / Gallery → every item title, extension label and the view-switcher's
      inactive icons are legible against the dark surface; repeat in light mode and confirm
      the switcher shell and Kanban drag preview are still visible
```

The marker is omitted on purpose. A ticked `**Smoke #184:**` line is exactly what authorizes
`/pr-closeout` to close #184, and this issue must stay open until every darkmode gap is
squashed. Written as a plain checklist line it still gates the merge without arming the
closer. If a future run ever *does* finish the whole checklist, that is the moment to add
the marker.

## #70 — Dramatic unblurred and ungraceful Mermaid editing

**Reported:** 2026-06-13 · **Labels:** `bug`, `Visualizations`

**Symptom.** Every keystroke in the Mermaid editor that leaves the source temporarily
invalid — which is most keystrokes, mid-word — produces a loud error, and the reporter
counts three of them at once. The diagram area is replaced by a red panel while typing, so
the thing being edited vanishes exactly when it is needed for reference.

**Where it lives.** One component, used by all three surfaces — the standalone
visualization, the fullscreen view, and the in-note embed (`mermaid-block.ts` renders "the
full MermaidViewer at a fixed height", per its own header comment at
`lib/domain/editor/extensions/blocks/mermaid-block.ts:1-19`). So a single fix covers every
report site.

- `components/content/viewer/MermaidViewer.tsx:186-212` — `handleSourceChange`. `setSource`
  at `:189` fires **synchronously on every keystroke**. Only the *save* is debounced
  (`:110-141`, 2 s) — nothing debounces validation.
- `:224-271` — the render effect, dep array `[source, mermaidReady, isEditMode,
  resolvedTheme]`. It therefore re-runs per keystroke.
- `:232` — `mermaid.parse(source)` throws on the intermediate text.
- The catch block then lights up **three surfaces at once**, which is the reporter's "3
  repeating errors":
  1. `:249` `setRenderError(...)` → the strip under the textarea at `:542-546`
  2. `:252-255` `toast.error("Mermaid Syntax Error", { duration: 5000 })` — a 5-second
     toast, re-fired faster than it expires
  3. `:258-266` overwrites `previewRef.innerHTML` with a full red panel, destroying the
     last good render

**Diagnosis.** Confirmed against the code, not a hypothesis. Validation is coupled 1:1 to
keystrokes and every failure fans out to three independent surfaces, none of which knows
about the other two.

**Approach.** Two changes, both in `MermaidViewer.tsx`:

1. **Debounce validation, not typing.** Introduce a `deferredSource` (a debounced mirror of
   `source`, ~600–800 ms) and make the render effect depend on *that*. The textarea keeps
   binding to `source`, so typing stays instant.
2. **Keep the last good diagram and collapse to one error surface.** Stop overwriting
   `previewRef.innerHTML` on failure — leave the previous SVG in place and dim it
   (`opacity-50 transition-opacity`, which is the reporter's "blur"). Drop the `toast.error`
   from the render path entirely and keep only the inline strip at `:542-546`. The toast is
   the worst of the three: it is global, it outlives the keystroke that caused it, and it
   fires on a surface the user is already looking at.

**The one constraint that could invalidate this:** debounce the *validation and render*
only. The Y.Doc write at `:196-202` must stay on the keystroke path — that is the
collaborative source of truth for the embed (`blockMermaid:{blockId}` on the note's Y.Doc),
and delaying it would drop characters from the CRDT under concurrent editing. Do not move
the `boundYdoc.transact` behind the new debounce.

Alternatives considered and rejected:

- **A literal 3-second blur, as the issue asks.** Three seconds is long enough that the
  preview feels frozen on *valid* edits too, since the effect cannot know in advance whether
  the next keystroke fixes the syntax. A shorter debounce plus "keep the last good render"
  delivers what the reporter actually wants — never seeing the error mid-word — without
  stalling the happy path.
- **Toast only, no inline error.** The issue floats this ("Consider only using toaster or
  one compact inline error surface"). Rejected: the toast is the surface that cannot be
  positioned next to the offending line, and in the note-embed case it appears far from the
  block being edited. The inline strip at `:542` is already the compact surface.

While in this catch block, note that `errorMessage` is interpolated raw into `innerHTML` at
`:258-266`. The string comes from Mermaid, so this is not a live user-input injection, but
if step 2 is implemented as written that template disappears anyway — do not carry it
forward into the new code path.

**Gates.** `pnpm typecheck` → `pnpm lint` (watch `react-hooks/exhaustive-deps` — swapping
the effect's `source` dep for `deferredSource` is the kind of change the React Compiler
flags; fix the dep array rather than suppressing) → `pnpm build`. No named static gate
covers the visualization surface. Smoke all three surfaces, since they share the component.

```markdown
- [ ] **Smoke #70:** open a Mermaid diagram and type an invalid character mid-edit → the last valid diagram stays on screen dimmed, no toast appears, and a single inline error shows under the textarea only after typing stops
```

## Likely already fixed

Bugs whose failure path appears to be gone from current code, with the commit that closed
it. The owner verifies and closes; this document never closes anything itself.

| Issue | Evidence it is fixed |
|---|---|
| #185 | `ed4374a` (2026-09-02) + `8dffeba` (2026-09-02), both ancestors of `origin/main`, rewrote `?search=` ranking in `app/api/content/content/route.ts:263-336` — the route the AI `@` picker calls (`lib/domain/ai/use-conversation-engine.ts:1453`) |

**Why this is a named cause and not an impression.** `ed4374a`'s message describes #185's
exact failure: "typing @Test in the mention picker showed only date-titled notes while the
note literally named 'Test' never appeared", because the search OR-clause matched **body
text** while ordering stayed alphabetical with `take=8`. That mechanism is specifically
worse for the *one-word* names #185 reports — a short common word like "Services" appears
inside many note bodies, so the body-matches filled the page and paged the exact title match
away, while a multi-word folder name has few body collisions and surfaces fine. `8dffeba`
then made each relevance tier its own query (`:286-327`: exact title → prefix → contains →
body-only fill), so an exact title match can no longer be truncated, and the picker limit
went from 8 to 16 (`use-conversation-engine.ts:1454`). Folders are not filtered out
anywhere on this path — the route applies no `contentType` filter unless `?type=` is passed,
and the engine does not pass it.

**What the owner should still check before closing**, since #185 was filed 2026-08-27 and
these commits landed 2026-09-02 against a differently-worded report: type `@Services` (or
any one-word folder name) in AI chat and confirm the folder appears. The issue also asks to
watch for file-name regressions — the same tiered path serves both, so one check covers it.
