## #223 — Shortkey for closing a tab doesn't fully close out a tab

**Reported:** 2026-09-12 · **Labels:** `bug`

**Symptom.** Pressing the close-tab chord clears the pane's content and shows the editor
loading skeleton, but the tab (screenshot: `Sept 11, 2026`) stays in the tab rail. Expected:
the tab disappears and the pane falls back to the next available tab.

**Where it lives.**

- `components/content/headers/MainPanelHeader.tsx:660-683` — the chord handler. It binds
  `Cmd/Ctrl+Alt+W` and `Cmd+Ctrl+W`, guards on `isActivePane`, and calls
  `closeContentTab(pane.activeTabId)`.
- `components/content/headers/MainPanelHeader.tsx:875` — the per-tab `X` button, which the
  owner reports as working, calls the *same* action with `tab.id`.
- `components/content/headers/MainPanelHeader.tsx:337` — `isActivePane = activePaneId === paneId`.
- `components/content/headers/MainPanelHeader.tsx:398-404` — the rail is rendered purely from
  `pane.tabIds` × `state.tabs`, both content-store state. Nothing else feeds it.
- `state/content-store.ts:1724-1805` — `closeContentTab`. Deletes the tab, filters it out of
  every pane and every layout snapshot, then recomputes the selection.
- `state/content-store.ts:1729` — `rememberIntent(tab.contentId, "close")`, the close
  tombstone that stops a workspace reconcile from resurrecting the tab.

**Hypothesis** (not confirmed — the two paths share one action, so the divergence is in
*which* tab the chord targets or in what happens right after).

Two candidate mechanisms, and they call for different fixes:

1. **The chord closes a different pane's tab.** The handler only binds when
   `isActivePane` is true and always targets *this* header's `pane.activeTabId`
   (`MainPanelHeader.tsx:662-665`). In a split layout, if `activePaneId` has not followed the
   pane the user is actually looking at, the chord closes the other pane's active tab. The
   pane in view then re-selects (skeleton) while the tab the user meant to close stays put —
   which is exactly the reported shape. The `X` button never has this problem because it
   carries its own `tab.id`.
2. **The selection lands on a tab that no longer belongs to the resolved pane.**
   In `closeContentTab`, `nextSelectedContentId` is only updated inside the
   `paneId === state.activePaneId` branch (`content-store.ts:1749-1754`); afterwards
   `resolveActivePaneForLayout` may pick a *different* pane and the final selection is
   `activeTab?.contentId ?? nextSelectedContentId` (`content-store.ts:1798`). When that
   fallback fires, selection can keep pointing at content whose tab is gone — the panel
   fetches it (skeleton) and a subsequent workspace reconcile re-adds it as
   `activeContentId`, which `restoreContentWorkspace` is documented to do for an id that
   belongs to no pane (`extensions/workplaces/state/workspace-store.ts:815-818`).

**The named uncertainty:** which layout the owner was in. Mechanism 1 needs a split layout
and is impossible in `single`; mechanism 2 needs at least two panes as well. If the report
came from a single-pane window, both are wrong and the next place to look is the
workspace-reconcile round trip, not the close action.

One thing ruled out by reading: the rail is not fed by the workspace store, so "the tab
never left the rail" cannot be a stale-render problem — the tab is either still in
`pane.tabIds` or was put back there.

**Approach.** Make the chord target the tab the user is looking at rather than the tab the
store believes is active:

- Give the chord handler the same identifier the `X` button uses. The simplest version is to
  resolve `activeTabId` inside the handler from `useContentStore.getState()` at keypress time
  instead of closing over `pane?.activeTabId` at effect-setup time, and to key the guard on
  the pane under the pointer/focus rather than `activePaneId`.
- Then close the selection hole in `closeContentTab`: when the resolved pane has no active
  tab, the selection should become `null`, never the pre-close `nextSelectedContentId`. That
  removes the "selected content with no tab" state that mechanism 2 depends on and that
  `restoreContentWorkspace` is documented to resurrect.

*Rejected — adding a `persistQuietly` call after the chord's close*, mirroring the
clear-all-tabs path (`extensions/workplaces/shell/WorkplacesShellNavigationTrailingControls.tsx:300-309`).
The `X` button does not persist either and works, so persistence is not the difference; and
an extra write would race the debounced workspace write rather than replace it.

*Rejected — suppressing the skeleton when selection is null.* `MainPanelContent.tsx:2338`
already returns the welcome screen before the `isLoading` branch at `:2351`, so a null
selection cannot render a skeleton. Chasing the skeleton is chasing a symptom of a
non-null-but-wrong selection.

**Worth fixing while you are in there (do not let it grow the PR):** the `!selectedContentId`
early return in the content-fetch effect (`MainPanelContent.tsx:516-527`) is the only branch
there that does not call `setIsLoading(false)` — the `person:` and `dm:` branches just below
it both do. It is unreachable today only because of the render ordering above. Left alone it
becomes a real stuck skeleton the moment those two returns are reordered.

**Gates.** `pnpm typecheck` → `pnpm lint` → `pnpm build`. No schema change, no new TipTap
node, no new publishing block, so no static gate beyond the build's own
`collab:schema:check`. Browser smoke is the real verification here.

```markdown
- [ ] **Smoke #223:** open two tabs in one pane, press the close-tab chord on the active one → that tab leaves the rail and the previously-viewed tab renders its content (no skeleton left behind); repeat in a dual-pane layout with the *other* pane focused → the chord closes the focused pane's tab, not the other pane's
```

## #70 — Dramatic unblurred and ungraceful Mermaid editing

**Reported:** 2026-06-13 · **Labels:** `bug`, `Visualizations`

**Symptom.** Every keystroke in the Mermaid source editor that leaves the diagram
temporarily invalid produces three simultaneous error surfaces, and the previously-valid
diagram is wiped instantly. The owner asks for a grace period ("blur temporary changes for
at least 3 seconds"), graceful messages, and *one* error surface rather than three.

**Where it lives.** `components/content/viewer/MermaidViewer.tsx`, and it is one file for
both reported surfaces — the note embed renders the same component
(`lib/domain/editor/extensions/blocks/mermaid-block.ts:17`, "expanded — renders the full
MermaidViewer at a fixed height").

- `MermaidViewer.tsx:223-269` — the render effect. Deps are `[source, mermaidReady, isEditMode, resolvedTheme]`;
  `source` changes on **every keystroke** via `handleSourceChange` (`:186-211`), and there is
  no debounce on this effect. `debouncedSave` at `:110` debounces the *save*, not the render.
- `MermaidViewer.tsx:232` — `await mermaidRef.current.parse(source)` runs per keystroke.

The three surfaces, all in the same `catch`:

| # | Surface | Line |
|---|---|---|
| 1 | `toast.error("Mermaid Syntax Error", …)`, 5s, **no toast id** | `MermaidViewer.tsx:252-255` |
| 2 | Inline error card injected straight into `previewRef.innerHTML`, replacing the last good SVG | `MermaidViewer.tsx:259-266` |
| 3 | `setRenderError(errorMessage)` → a second inline banner | `MermaidViewer.tsx:249` rendered at `:542-545` |

**Diagnosis** (confirmed against the code — this is not a hypothesis). The "3 repeating
errors" in the screenshots are those three surfaces firing together, and they repeat because
the effect re-runs unthrottled per keystroke. Because `toast.error` is called without an id,
sonner stacks a new toast per keystroke instead of replacing the previous one — that is the
"long noisy" part. The diagram vanishes because the error branch overwrites
`previewRef.innerHTML` with the error card; the last good SVG is only preserved on the
success path (`:235-238`).

**Approach.**

1. **Debounce the render**, not just the save. Wrap the effect body in a ~500ms timer keyed
   on `source` with a cleanup that clears it, so a run of keystrokes produces one parse.
2. **Hold the last good render through the grace period.** On a parse failure, leave the
   existing SVG in `previewRef` and apply a dimming/blur class to the preview container
   instead of replacing its `innerHTML`. This is the owner's stated requirement and it also
   removes the flash-of-nothing between valid states.
3. **Collapse to one surface.** Keep the `renderError` state banner (`:542-545`) as the single
   compact inline surface — it is already React-rendered and already carries `.dark`
   companions — and delete both the `toast.error` call and the `innerHTML` error-card
   injection. If a toast is wanted for the standalone viewer, give it a stable id
   (`toast.error(msg, { id: \`mermaid-${contentId}\` })`) so repeats replace rather than stack.

*Rejected — keeping the toast and dropping the inline surfaces.* The embedded block is often
short; a toast that fires per edit on a note the user is writing is exactly the "takes up
available space in the toaster surface" the issue complains about. The owner's own
"Considerations" allow either, and the inline banner is the one that stays scoped to the
block.

*Rejected — raising the debounce to 3s to match "at least 3 seconds".* Three seconds of
grace applies to *how long the stale diagram stays visible*, not to how long a valid edit
waits to render. A 3s render debounce would make correct edits feel broken; the blur-hold
delivers the requirement without the latency.

**Worth fixing in the same PR (one line, same block of code):** `errorMessage` is
interpolated into `previewRef.innerHTML` unescaped at `MermaidViewer.tsx:262`, and Mermaid's
parse errors echo the offending source back. Step 3 deletes that injection entirely, so the
fix is free — just do not reintroduce the pattern in the blur-hold implementation.

**Gates.** `pnpm typecheck` → `pnpm lint` → `pnpm build`. If the blur-hold introduces a new
CSS rule with an extreme colour, it needs a `.dark` companion (CLAUDE.md, dark-mode rule) —
prefer a Tailwind opacity/blur utility over a new `globals.css` rule and the question does
not arise. There are committed Mermaid snapshots
(`tests/e2e/__snapshots__/editor/per-block.spec.ts/editor-mermaid-block-{light,dark}.png` and
the publishing pair), so run `pnpm test:e2e` and regenerate only if the *valid* rendered
state actually changed — it should not.

```markdown
- [ ] **Smoke #70:** open a Mermaid block, delete the arrow from a valid `graph TD; A-->B` → the previous diagram stays visible (dimmed) for the grace period, exactly one error surface appears, and holding the broken state for ten seconds produces no stack of toasts
```

## #184 — Darkmode contrast issues (folder affordances)

**Reported:** 2026-08-27 · **Labels:** `bug`

**Symptom.** The dark-mode rollout left theme gaps. The issue is a standing checklist; the
one item currently listed is **"Folder affordances, including various folder views"**, with
two screenshots of folder view surfaces.

**Where it lives.** Folder-view surfaces still carry translucent-white overlay classes with
no theme companion — styling written when the app was dark-only, so the class *is* the
dark-mode value and the light theme has nothing:

- `components/content/folder-views/ListView.tsx:167` — `border-white/10 hover:bg-white/5` on
  the row button, over a `glass0` background. This is the row affordance in the owner's
  screenshots.
- `components/content/folder-views/DashboardView.tsx:248` — `border-white/10 … bg-white/5`
  on the widget drag handle.
- `components/content/folder-views/DashboardView.tsx:262` and
  `components/content/folder-views/KanbanView.tsx:122` — `hover:bg-white/20` on the
  remove/close buttons.
- `components/content/folder-views/CanvasView.tsx:124` — `hover:bg-white/50`, the most
  extreme of the set.

Twenty such single-theme declarations across `components/content/folder-views/` and
`components/content/file-tree/` (`grep -rn "bg-white/\|border-white/\|text-white\b" … | grep -v "dark:"`),
so the list above is the folder-view subset, not the whole count.

**Diagnosis.** These are single-theme rules, not contrast-ratio misses. The fix is to give
each a paired light value (`bg-black/[0.04] dark:bg-white/5`, `border-black/10 dark:border-white/10`)
rather than to retune a token. The design-token layer (`lib/design/system/`) is not at fault
and should not be edited for this — the issue's own "we try at all costs to modify the
existing design system" reads as *reuse* it, and these call sites bypass it with raw Tailwind.

**One confirmed false positive, leave it alone:** `KanbanView.tsx:479-480` (`bg-white` +
`text-gray-900`, no `dark:`) carries a comment at `:474-477` stating the drag preview is
deliberately light in both themes. Any audit sweep will flag it; it is correct as written.

**The named uncertainty:** I could not view the issue's attached screenshots, so I matched
"folder affordances" to the folder-view row/handle/close controls by name. If the
screenshots are of the folder *icon* affordances in the file tree instead, the same class of
defect applies but the call sites are in `components/content/file-tree/`.

**Approach.** Timebox to the single ticked checklist item. Sweep
`components/content/folder-views/` for `bg-white/`, `border-white/`, `text-white` and
`hover:bg-white/` declarations lacking a companion, pair each, and verify both themes with
`themedGoto`. Leave the rest of the umbrella issue's future items alone.

*Rejected — adding an app-wide audit script.* `pnpm publishing:audit:themes` already does
exactly this shape of scan but is scoped to `.public-prose .block-*` rules in `globals.css`;
widening it to Tailwind class strings in `.tsx` is a different tool with a much worse
false-positive rate (the `KanbanView` case above is the proof). Propose it separately if the
sweep turns out to be recurring work — not inside a contrast fix.

**Gates.** `pnpm typecheck` → `pnpm lint` → `pnpm build`. Visual: folder views are behind
auth, and `tests/e2e/dark-mode/authenticated-routes.spec.ts` is still `test.skip` pending the
auth fixture, so there is **no** snapshot coverage for these surfaces — manual two-theme
verification is the only gate. Do not regenerate unrelated baselines.

> **Do not tick this line for closure.** #184 is an explicit standing issue — "a series of UI
> work that should never be closed until darkmode contrast issues are fully squashed". A
> ticked `Smoke #184` line authorises `/pr-closeout` to close it, which is the opposite of
> what the owner asked for. Either omit the marker from the fixing PR and reference the issue
> in prose, or leave the line unticked deliberately.

folder … not appearing despite verbatim matching". The route now fetches exact-title matches
as their own first tier (`app/api/content/content/route.ts:285-291`), prefix second
(`:292-306`), contains third (`:307-318`), body-only last (`:319-325`). #185 was filed
2026-08-27; both commits land 2026-09-02, after it.

Nothing on the client side filters folders out of the result — `handleMentionSearch` maps the
route's items straight through (`lib/domain/ai/use-conversation-engine.ts:1613-1621`) and
`ChatSuggestionMenu` renders every item, with a dedicated folder icon
(`components/content/ai/ChatSuggestionMenu.tsx:46-47`). So the ranking was the only place the
folder could have been lost.
