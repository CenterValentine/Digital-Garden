## #85 — Uploading image under view places file at file tree root

**Reported:** 2026-06-23 · **Labels:** `bug`, `Filetree`, `File Upload`

**Symptom.** In a workspace scoped to a view root, `+` → File (upload) puts the file at
the real vault root instead of the view's root, where it is invisible from the view the
user is looking at.

**Where it lives.** The header `+` and the tree's context menu open *two different*
`FileUploadDialog` instances, and only the tree's path was fixed.

Broken path (header `+`):

- `components/content/headers/LeftSidebarHeader.tsx:370` → `onCreateFile`
- `components/content/LeftSidebar.tsx:288` → `handleCreateFile`
- `components/content/LeftSidebar.tsx:122-125` — sets `fileUploadParentId` to a literal
  `null`, with the original `// TODO: Get from current selection?` still in place
- `components/content/LeftSidebar.tsx:346` — that `null` becomes the dialog's `parentId`
- `components/content/dialogs/FileUploadDialog.tsx:62` seeds `selectedFolderId` from it;
  `:200` omits `parentId` from the body when falsy
- `app/api/content/content/upload/simple/route.ts:292` — `parentId: parentId || null`,
  i.e. vault root

Working path (tree / context menu), for contrast:

- `components/content/content/LeftSidebarContent.tsx:2426` —
  `setUploadDialog({ open: true, parentId: requestedParentId ?? scopedRootParentId })`
- `components/content/content/LeftSidebarContent.tsx:323` —
  `const scopedRootParentId = effectiveViewRootContentId`

**Diagnosis.** `7497020` (2026-08-25, merged via PR #177 / `b5630b0`) introduced
`scopedRootParentId` and remapped top-level writes in a scoped tree onto the view root —
creates, moves, drops, and the tree's upload entry point. It did not touch
`LeftSidebar.handleCreateFile`, which owns the header `+` and still hard-codes `null`.
`LeftSidebar`'s dialog *is* correctly targeted for drag-and-drop (`LeftSidebar.tsx:263-269`,
where the tree resolves the destination first) — the header is the only remaining caller
passing an unconditional `null`.

**Approach.** Give the header path the same fallback the tree path already has. The
snag is that `scopedRootParentId` is derived inside `LeftSidebarContent`, one level below
`LeftSidebar`. Cheapest correct fix: read the same two workspace-store selectors in
`LeftSidebar` (`activeWorkspaceIsView`, `activeViewRootContentId`, per
`LeftSidebarContent.tsx:280-311`) and seed `fileUploadParentId` from them.

Rejected: (a) lifting `scopedRootParentId` into a shared hook — right long-term shape,
but it touches the scope-override state machine including the ephemeral `scopeOverride`,
which is more surface than this bug needs; (b) routing the header `+` through
`LeftSidebarContent.handleCreate` like the other create types — architecturally the
tidier answer, and worth doing eventually, but it moves a dialog between components and
risks the drag-and-drop path that currently works. Prefer (a) as a follow-up once this
is green.

Note the duplicate-dialog structure is the actual root cause; a comment pointing the next
reader at it is worth more than the one-line diff.

**Gates.** `typecheck` → `lint` → `build`. No schema, no new TipTap node, no new
publishing block. Browser smoke is the real gate here.

```markdown
- [ ] **Smoke #85:** in a workspace scoped to a view root, click the sidebar header `+` → File (upload) and upload a file → it appears at the top of the scoped tree, and in the unfiltered workspace it sits under the view root folder, not the vault root
```

## #61 — Browser extension: pasted image preview/persistence broken

**Reported:** 2026-06-11 · **Labels:** `bug`, `browser extension`

**Symptom.** Paste an image into a note inside the browser-extension iframe; it previews
fine, but after a reload or a cleared session the preview is broken.

**Where it lives.**

- `lib/domain/editor/hooks/use-image-paste.ts:66-112` — `insertImageFromFile` inserts the
  node with `src: URL.createObjectURL(file)` and `uploading: true`, then swaps `src` to
  the server `downloadUrl` when the upload resolves (`:79-96`) or deletes the node and
  toasts on failure (`:97-110`)
- `lib/domain/editor/hooks/use-image-upload.ts:33-37` — the upload itself, with
  `credentials: "include"`
- `lib/domain/editor/extensions/image.ts:39-46` — the `uploading` attribute renders as
  `data-uploading` but does **not** gate persistence of `src`
- `app/embed/content/[id]/EmbedContentClient.tsx:4` — the embed mounts the same
  `MainPanelWorkspace`, so the paste path is shared with the app

**Hypothesis** (not confirmed against a running extension — see Blocked on). The
`blob:` URL gets persisted. There is no guard anywhere in `lib/domain/editor/` or
`lib/domain/collaboration/` against writing a `blob:` src — I grepped for one and found
nothing. A `blob:` URL dies with the page, which is exactly the reported shape: fine in
session, broken after reload.

Two candidate mechanisms, both consistent with the evidence:

1. **Autosave races the upload.** The 2-second autosave debounce fires between the
   optimistic insert and the upload resolving, persisting `src: blob:…`. In the extension
   iframe the upload is slower (cross-site, larger screenshots), so the race is much
   easier to lose there than in the app — which would explain why only the extension
   reports it.
2. **Cross-site cookie loss.** The iframe runs on a third-party origin, so
   `credentials: "include"` only carries the session cookie if it is `SameSite=None;
   Secure` *and* the browser allows third-party cookies. If it doesn't, the upload 401s.
   On its own this predicts the node being deleted with an error toast rather than a
   broken preview (`:97-110`), so it is likely a contributing factor rather than the whole
   story — unless an autosave already committed the blob src before the delete.

Mechanism 1 explains the symptom without further assumptions; check it first.

**Approach.** Regardless of which mechanism dominates, the durable fix is the same guard:
never let a `blob:` src reach persistence. Either strip/skip image nodes with
`uploading: true` in the save path, or hold the autosave while any node has
`uploading: true`. Prefer the strip — holding the autosave couples an unrelated subsystem
to upload state, and a hung upload would then block all saving.

Then, separately, confirm whether the extension's uploads are authenticating at all; if
not, that is its own fix and this issue should spawn a sibling.

Collaboration constraint: images inside a collaborative note must be corrected **through**
the Y.Doc, never by writing the payload and reseeding — see
`docs/notes-feature/core/CONTENT-LOAD-CASCADE.md` §9.4. The existing `setNodeMarkup`
dispatch at `use-image-paste.ts:81-92` is already the right shape; keep the fix on that
side rather than adding a payload-level repair.

**Gates.** `typecheck` → `lint` → `build`. Touching the save path means a smoke test in
the app as well as the extension, to check no regression in ordinary image paste.

```markdown
- [ ] **Smoke #61:** paste a screenshot into a note in the browser-extension iframe, wait for the spinner to clear, reload the page → the image still renders (and its `src` is `/api/content/content/<id>/download`, not `blob:`)
- [ ] **Smoke #61b:** paste an image into a note in the main app, reload → still renders; no regression
```

**Blocked on.** I could not reproduce this from a headless session — it needs the
extension loaded in a real browser on a third-party site. Two things to observe when you
do: whether the upload request returns 401 in the iframe (settles mechanism 2), and
whether the persisted note JSON contains a `blob:` src (settles mechanism 1). The owner
comment on the issue notes it has not recurred since filing, so a "cannot reproduce"
outcome is a legitimate result here — worth timeboxing before the fix.

## #65 — Audio TTS reader falls back to browser voices in production

**Reported:** 2026-06-12 · **Labels:** `bug`, `TTS`

**Symptom.** BYOK "pretty voices" work locally but production plays the browser's OS
voice with a broken-wifi indicator and no explanation. The user cannot tell whether a key
expired, billing lapsed, or the network failed.

**Where it lives.** `lib/features/tts/controller.ts:186-227`, `attemptPlayback` — the
documented "fallback policy" block at `:168-186` is the tunable knob.

The exact line that loses the information, at `:215-217`:

```ts
if (isWebSpeechAvailable()) {
  playWebSpeech(text, options.webVoiceUri);
  return;               // <- cloudError discarded
}
```

`cloudError` is captured at `:206-211` and then used **only** if Web Speech is *also*
unavailable (`:219-226`). On any desktop browser Web Speech is always available, so the
cloud error is always discarded.

**Diagnosis.** Confirmed, and this is a design decision rather than an accident — the
policy comment at `:176-181` says so explicitly ("the cloud error is surfaced only if Web
Speech is also unavailable") and even lists the alternative the issue is asking for
("Treat a 422 (no key configured) as a hard error with a setup hint"). The issue is
asking for that listed alternative, softened: degrade *and* explain, rather than degrade
silently.

`git log --since=2026-06-12 -- lib/features/tts app/api/ai/speech` returns **zero
commits**, so nothing has changed here since the report. This is definitively live.

**Approach.** Keep the fallback — the user should still hear something — but stop
throwing away `cloudError`. Put it in the store alongside `engine: "webspeech"` (a
`degradedReason` field next to the existing `error`, so a degraded-but-playing state is
distinct from a hard error), and have the mini-player surface it on the existing
broken-wifi indicator as a tooltip plus a link to settings when the reason is a
credential or billing failure. That needs `getSpeechBlob` to preserve enough of the
server's status to distinguish 401/422/429 from a generic network failure — check what
`SpeechSynthesisError` (referenced at `:209`) already carries before adding a field.

Rejected: making a 422 a hard error with no audio. It matches the policy comment's first
alternative, but it trades a confusing experience for a broken one, and the issue asks to
understand the failure, not to be denied playback.

Note the issue's second observation — "Cannot have two HTML5 backends at the same time",
unreproducible — is a separate defect. Do not fold it in; if it surfaces while testing,
file it.

**Gates.** `typecheck` → `lint` → `build`. Any new CSS for the indicator needs a `.dark`
companion. The real gate is a production smoke, since this reproduces only there.

```markdown
- [ ] **Smoke #65:** on production with a deliberately invalid TTS key, click "listen" on a note → audio still plays via the browser voice AND the mini-player indicator explains the cloud failure (expired/invalid key) with a link to settings
```

**Blocked on.** Reproducing the *original* prod failure needs a real BYOK provider in a
failing state. Forcing an invalid key is the cheap substitute and exercises the same
branch, but it won't tell you why the key was failing in prod in the first place — if the
underlying cause still matters, capture the server response from `/api/ai/speech` in prod
before changing anything.

## #80 — AI flashcard gen tool rejects sole root decks

**Reported:** 2026-06-20 · **Labels:** `bug`, `TTS` *(label looks wrong — this is flashcards/AI tools)*

**Symptom.** Asking the AI to generate cards for an existing root deck (e.g. "Machine
Learning", no subdeck) and accepting onto that deck fails instead of adding the cards.

**Where it lives.**

- `app/api/flashcards/decks/route.ts:344-372` — `POST` creates unconditionally and maps
  the unique-constraint violation to a hard 409, *"A deck with this name already exists at
  that level."* There is no idempotent "return the existing deck" branch.
- `components/content/ai/FlashcardCardProposalList.tsx:546-556` — the cards flow skips
  creation when `effectiveDeckExists`, and surfaces the server message verbatim on failure
  (`:578-583`)
- `components/content/ai/FlashcardDeckProposalCard.tsx:104-107` — the bare-deck flow is
  stricter, refusing before any request:
  ```ts
  if (effectiveDeckExists) { toast.error("This deck already exists."); return; }
  ```
- `lib/domain/ai/tools/flashcard-tools.ts:500-503` — the server tool sets `deckExists` by
  matching `path: proposedPath` exactly

**Diagnosis.** The whole thing turns on `effectiveDeckExists` resolving true, and that is
an **exact** path-string match — `flashcard-tools.ts:500` on the server, and
`FlashcardCardProposalList` / `FlashcardDeckProposalCard` client-side via
`existingDecks.find((d) => d.path === slugged)`. Whenever the AI's `proposedPath` slugs to
something even slightly different from the stored path, `deckExists` is false, the client
takes the create branch, and the server 409s. The user sees a deck they can see in the
sidebar being rejected as un-creatable — which is what this issue describes.

Marked **Diagnosis** rather than Hypothesis for the failure mechanism, but the *trigger*
(what made "Machine Learning" mismatch) is unconfirmed — see Blocked on.

Two things it is **not**:

- Not already fixed. `git log --since=2026-06-19` over `app/api/flashcards/`, both
  proposal components, and `flashcard-tools.ts` returns exactly one commit — `660b8ba`
  (2026-07-16), a sidebar layout change.
- Not the skip-create branch. That landed in `6fefe96` on **2026-06-18**, two days
  *before* the report, so it was already live when the failure happened.

The issue's `/` note *does* look fixed: segments are slugified and empties dropped
(`segments = slugged.split("/").filter(Boolean)`), so a trailing `/` no longer mints a
phantom "Deck" subdeck. Worth confirming in the smoke.

**Approach.** Make the server idempotent: on the unique-constraint violation, look up the
existing sibling and return it with 200 rather than 409. That fixes every caller at once,
including whichever path-mismatch triggers it, and matches what the user means by
"accept onto the existing deck". Then drop the pre-flight refusal at
`FlashcardDeckProposalCard.tsx:104-107` so the bare-deck card can also land on an existing
deck.

Rejected: fuzzy-matching proposed paths against existing decks client-side. It makes
`deckExists` right more often but leaves the 409 reachable, and a near-match that silently
retargets someone's cards to the wrong deck is worse than the current error.

Also worth doing while here: the `TTS` label on this issue looks like a mis-file. Not
relabelling — no authorization for that — just flagging it.

**Gates.** `typecheck` → `lint` → `build` → `pnpm ai:drift:check` (the AI-drift gate is
path-filtered onto `lib/domain/ai/**`, so it fires if the tool definition changes). No
migration: this is a query/response change, not a schema change.

```markdown
- [ ] **Smoke #80:** with an existing root deck "Machine Learning" and no subdecks, ask the AI to generate 3 cards on it and accept → the 3 cards land in the existing deck, no new deck is created, and no "already exists" error appears
- [ ] **Smoke #80b:** repeat with a trailing slash in the deck path field → no phantom "Deck" subdeck is created
```

**Blocked on.** I could not determine *which* mismatch fired for "Machine Learning" —
that needs the actual proposed path from a live run against GPT-4o. The idempotent-server
fix doesn't depend on knowing, but capturing it would confirm whether a second,
path-normalization bug is hiding behind this one.

## #179 — Chat summary detail card is not showing for long chats

**Reported:** 2026-08-27 · **Labels:** `bug`

**Symptom.** Hovering the assistant avatar shows the provider/model/token card on short
chats but nothing on long ones.

**Where it lives.** `components/content/ai/ChatMessage.tsx:1845-1945`, the assistant
avatar tooltip.

- `:1888-1894` — `handleEnter` anchors the card from the avatar's rect:
  ```ts
  setTooltipAnchor({ top: rect.bottom + 6, left: rect.left });
  ```
- `:1930-1937` — rendered into a body-level portal with `position: "fixed"`, at exactly
  those coordinates, `zIndex: 9999`

**Diagnosis.** Confirmed against the code, and it matches the reporter's own guess. The
anchor is computed once, downward-only, with **no viewport-edge detection and no
clamping**. In a long chat the newest assistant avatar sits near the bottom of the scroll
container, so `rect.bottom + 6` lands below the viewport; the card renders off-screen. On
a short chat the avatar is high enough that the same math stays on-screen. The comments at
`:1931-1932` explain that `position: fixed` immunises it from ancestor clipping — true,
and precisely why the failure is silent: nothing clips it, it is simply painted outside
the viewport.

**Approach.** Reuse `lib/core/menu-positioning.ts`, which already does two-phase
measure-then-position with boundary detection and edge flipping, and is what the context
menus and dropdowns use — `anchorMenuAbove` (`:187`) is the flip case this needs, and
`calculateMenuPosition` (`:77`) the general one. `CLAUDE.md`'s "prefer the existing
library over a bespoke build" rule points straight at it; hand-rolling a
`window.innerHeight` check here would be a third copy of logic the repo already owns
twice.

One wrinkle: the tooltip is `pointer-events-none` and sized by content, so it needs the
measure phase (render hidden, measure, position) rather than an assumed height. Check
whether `calculateMenuPosition` accepts a measured `MenuDimensions` — it takes a
`MenuDimensions` per `:42-47`, so measuring first is the expected call shape.

Rejected: clamping `top` to `window.innerHeight - height`. One line, but it slides the
card over the avatar the user is pointing at, and it wouldn't fix the same latent bug on
the horizontal axis in a narrow side panel.

**Gates.** `typecheck` → `lint` → `build`. New positioning styles are inline, not CSS, so
no `.dark` companion is needed — but confirm the card still reads correctly in both
themes, since it already carries explicit light/dark classes at `:1938`.

```markdown
- [ ] **Smoke #179:** in a chat long enough to fill the panel, hover the last assistant avatar for ~1s → the provider/model/token card appears fully on-screen, flipped above the avatar rather than clipped at the bottom edge
```
