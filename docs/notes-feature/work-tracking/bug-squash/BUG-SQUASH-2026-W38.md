## #223 — Shortkey for closing a tab doesn't fully close out a tab

**Reported:** 2026-09-12 · **Labels:** `bug`

**Symptom.** Press the close-tab chord. The pane's content clears and is replaced by a
loading skeleton, but the tab stays in the header rail with its name intact (the report's
screenshot shows "Sept 11, 2026" persisting). Expected: the tab goes away and the pane
falls back to the next available tab.

**Where it lives.** Three files, and the interesting part is that the close itself is
correct — something puts the tab back.

The shortcut and the rail:

- `components/content/headers/MainPanelHeader.tsx:661-683` — the chord handler
  (`Cmd/Ctrl+Alt+W`, plus `Cmd+Ctrl+W` on macOS). It calls `closeContentTab(activeTabId)`
  and nothing else
- `:875` — the tab ✕ button calls the *same* `closeContentTab(tab.id)`. So this is not a
  shortcut-specific code path, which matters for the repro below
- `:398-403` — the rail is `useMemo` over `pane.tabIds` mapped through `state.tabs`. A tab
  removed from the store cannot linger here; a visible tab is a tab that is present in the
  store

The close is well-formed:

- `state/content-store.ts:1724-1808` — `closeContentTab` deletes the tab from `state.tabs`,
  filters it out of every pane's `tabIds`, does the same across `layoutSnapshots`, re-elects
  `activeTabId`, and records `rememberIntent(tab.contentId, "close")` at `:1729`
- `:1173-1187` — `commitWorkspace` runs `syncBrowserState` synchronously inside the
  `set` updater, so `?content=` / `tabs_*` are stripped from the URL in the same commit
  (`:1129-1170`), and `lastSelectedContentId` is removed from localStorage at `:1123`

**Hypothesis.** Not confirmed against a running app — I can read the resurrection paths but
not watch which one fires. Two candidates, and they are distinguishable in one step.

*Candidate 1 — the empty-workspace restore effect re-arms (primary).*
`components/content/MainPanelWorkspace.tsx:494-584` is written as a cold-load deep-link
restore, but it is guarded only by `if (openContentIds.length > 0) return;` at `:495` with
`openContentIds.length` in its dep array at `:584`. There is no mount-only ref. Closing the
**last** tab drives that length 1 → 0, so the effect re-runs as a *resurrection* effect. Its
terminal branch at `:580-583` reads `lastSelectedContentId` from localStorage and calls
`setSelectedContentId(lastSelectedId)` — reopening what was just closed. Its deep-link
branch at `:549-554` is worse: `markLocalOpenIntents` records an **open** intent, and per
`state/content-store.ts:487-489` the opposite intent *replaces* the close intent, so the
close loses its only protection against the next reconcile. The remembered title comes from
`saveStoredTabTitles` (`:1127`) via `loadStoredTabTitles` (`:1878`), which is exactly why
the rail shows the old name instantly while the pane sits on a skeleton.

This hinges on `syncBrowserState` and the effect racing — the URL/localStorage cleanup at
`:1120-1170` is meant to leave nothing to restore. Read that ordering first; if the cleanup
always wins, candidate 1 is dead and the answer is candidate 2.

*Candidate 2 — the workspace reconcile re-adopts from R1 membership.*
`extensions/workplaces/state/workspace-store.ts:462-478` unions
`workspace.membershipContentIds` into the pane set on every reconcile. The close intent does
filter it (`state/content-store.ts:1893-1902`), but only until the intent retires —
`confirmWorkspaceWrite` (`:502-509`), or the backstop at `:471`/`workspace-sync.ts:54`
(20 × the 15s poll = 5 minutes). If the close never reaches server-side membership, the tab
returns on the first reconcile after the intent expires. There is a documented hole here:
`workspace-store.ts:1283-1305` short-circuits extension surfaces to `PUT /tabs`, which the
comment at `:1286-1289` says is **deliberately additive** — "must never prune tabs only
wider surfaces have open". A close made in an extension panel iframe therefore never prunes
membership. The main window continues to the legacy `PATCH` that does dual-write membership,
so this candidate predicts the bug in the panel and not the app window.

**Approach.** Diagnose before fixing — the two candidates want different patches, and
candidate 2's fix is in extension-owned code with a spec comment explaining why it is the
way it is.

Two observations settle it, both from one session:

1. Close the **last** tab in a pane versus close one of **several**. Candidate 1 only fires
   when `openContentIds.length` reaches 0; candidate 2 does not care.
2. If it reproduces with several tabs open, time it. Candidate 2 cannot fire before the
   next 15s poll and usually needs the 5-minute backstop; candidate 1 is immediate.

For candidate 1, the fix is to stop the restore effect from re-arming: gate it on a
`useRef` that latches after the first run, so it stays the cold-load/deep-link restore its
comment says it is. *Rejected:* removing the localStorage fallback at `:580-583` — it is
load-bearing for a genuine cold load with no URL params, and deleting it trades this bug for
"reopening the app shows an empty pane". *Also rejected:* teaching the effect to skip ids
carrying a close intent — it would work, but it leaves a mount-only effect re-running on
every empty-pane transition, which is the actual defect.

For candidate 2, the fix is to emit the membership **close** event on the extension-surface
path. `extensions/workplaces/server/membership.ts:85` already documents an idempotent
close/remove; the additive `PUT` at `workspace-store.ts:1297-1302` needs a companion that
names the specific ids this surface closed, rather than a wholesale prune — the comment's
warning is about pruning tabs the panel never knew about, and an explicit per-id close does
not do that. Do **not** make the `PUT` authoritative; that is the exact regression
`:1286-1289` records (prod fix, PR #166).

Whichever it is, keep `rememberIntent` as-is. The intent system is not the bug — it is the
thing currently masking candidate 2 for the first five minutes.

**Gates.** `typecheck` → `lint` → `build`. No schema change, so no migration and no
`migration-drift` exposure. Not an editor or publishing change: `collab:schema:check` and
the publishing gates are untouched. Watch `react-hooks/exhaustive-deps` on the
`MainPanelWorkspace` effect if you add a latch ref — a ref is not a dep, but the effect's
existing deps should not grow.

```markdown
- [ ] **Smoke #223:** open two tabs, close the active one with the close-tab chord → it leaves the rail immediately and the other tab becomes active, with no loading skeleton
- [ ] **Smoke #223b:** close the last remaining tab with the chord → the rail is empty and stays empty for 30s (the tab does not reappear), and the pane shows the empty state rather than a skeleton
- [ ] **Smoke #223c:** same as #223b but using the tab's ✕ button → identical result, confirming the fix is not chord-specific
```

## #70 — Dramatic unblurred and ungraceful Mermaid editing

**Reported:** 2026-06-13 · **Labels:** `bug`, `Visualizations` · *open ~3 months; carried
over from W36, where it was dropped by the five-per-week cap*

**Symptom.** Editing a Mermaid diagram into a temporarily-invalid state (which is every
intermediate keystroke) fires a loud error per change — the reporter counts three surfaces
at once. The preview is replaced by a large red error card, a toast stacks up, and there is
no grace period while the user is mid-edit.

**Where it lives.** One component owns every mermaid surface — the note embed mounts the
same viewer (`lib/domain/editor/extensions/blocks/mermaid-block.ts:479` renders it into the
NodeView), so a fix here covers the editor, the standalone view and the fullscreen wrapper
at once.

- `components/content/viewer/MermaidViewer.tsx:224-271` — the render effect. Its dep array
  at `:271` is `[source, mermaidReady, isEditMode, resolvedTheme]`, and `source` is set
  synchronously per keystroke by `handleSourceChange` at `:186-212`. **There is no debounce
  on render** — the 2s debounce at `:110-135` is the *save*, not the render
- `:232` — `await mermaidRef.current.parse(source)` throws on invalid syntax, so every
  in-progress keystroke lands in the catch
- `:252-255` — surface 1: `toast.error("Mermaid Syntax Error")` with `duration: 5000`. At
  typing speed these queue up, which is the "3 repeating errors" in the report
- `:258-266` — surface 2: the preview's `innerHTML` is replaced with a full-size red card,
  so the diagram vanishes the instant the source stops parsing
- `:27-36` — `initializeMermaid`. `startOnLoad`, `theme`, `securityLevel` and `fontFamily`
  are set; **no error-suppression option**, which is the likely source of surface 3 (mermaid
  drawing its own error graphic)

The sibling that already does this right:

- `components/public/MermaidHydrate.tsx:39` — passes `suppressErrors: true` and treats a
  failure as "leave the `<pre>` showing raw source, log, move on" (`:42-51`). Same library,
  same failure, no user-facing noise

**Diagnosis.** Confirmed against the file. This is not one bug but three compounding
choices: render is not debounced, failure is treated as an event worth a toast, and failure
destroys the last good preview. Any one of them alone would be tolerable.

**Approach.** Three small changes in `MermaidViewer.tsx`, in order of value:

1. **Debounce the render.** Wrap the body of the effect at `:229-268` in a ~400-600ms timer
   cleared by the effect's cleanup. The issue asks for "at least 3 seconds"; that is too long
   for a valid edit to feel responsive, so the better shape is a short debounce for *success*
   and a longer grace period before *failure* is shown at all. Keep the existing dep array —
   a theme flip or edit-mode toggle should still redraw promptly.
2. **Stop toasting syntax errors.** Delete `:252-255`. A syntax error while typing is not an
   event; it is a state, and the inline surface already reports it. Keep the
   `clientLogger.warn` at `:241-247`. Per the issue's own "Considerations", one compact
   surface is the target.
3. **Keep the last good render.** Instead of overwriting `previewRef.innerHTML` at
   `:258-266`, leave the previous SVG in place and show the error as a small badge or a
   dimmed overlay, driven by the `renderError` state at `:92` that the component already
   holds but currently only mirrors. This is the "blur" the title asks for — the diagram
   stays visible and goes visually inert while the source is mid-edit.

Also check whether `suppressErrorRendering: true` belongs in `initialize` at `:29-34`, and
whether `parse` should take `{ suppressErrors: true }` so it returns false instead of
throwing — `MermaidHydrate.tsx:39` is in-repo proof the parse option exists on this version.
Confirm both against the installed mermaid (`^11.12.2`) before relying on them; the option
names have moved between major versions and `node_modules` was not available to verify here.

*Rejected:* validating in a worker or against a grammar before calling mermaid — a second
parser to keep in sync with the real one, for a problem a timer solves. *Also rejected:*
only rendering on blur or on an explicit "Run" button — it kills the live-preview feel that
is the reason to edit mermaid in this app rather than in a text file.

**Gates.** `typecheck` → `lint` → `build`. `MermaidViewer` is a client component reached
through the `mermaidBlock` NodeView, and no node, mark or attribute changes — so
`TIPTAP_SCHEMA_VERSION` stays put and `collab:schema:check` is unaffected. If step 3 adds
CSS with an extreme colour, it needs a `.dark` companion; prefer the existing
`dark:` utility pairs already used at `:260-263`. There are committed snapshots at
`tests/e2e/__snapshots__/editor/per-block.spec.ts/editor-mermaid-block-{light,dark}.png`
and `.../publishing/per-block.spec.ts/mermaid-block-{light,dark}.png` — the publishing ones
go through `MermaidHydrate`, not this component, so they should not move. If the editor
snapshots do move, that is an intentional visual change: regenerate with
`pnpm test:e2e:update` and review the PNGs before committing.

```markdown
- [ ] **Smoke #70:** open a Mermaid diagram, select all and type `graph TD\n  A[[` → no toast appears, the previously-rendered diagram stays on screen (dimmed or badged) instead of being replaced by a red card, and a single compact error surface names the syntax problem
- [ ] **Smoke #70b:** continue typing to `graph TD\n  A[Start] --> B[End]` → the diagram re-renders to the valid result within about a second and the error surface clears, with no queued toasts left behind
```
