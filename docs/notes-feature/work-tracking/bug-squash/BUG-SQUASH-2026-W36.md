## #183 — Children files persist after parent folder deletion

**Reported:** 2026-08-27 · **Labels:** `bug`

**Symptom.** Delete a folder that contains files, confirm, and the folder disappears — but
its children reappear at the top level of the file tree instead of going with it. The
reporter marks it a regression.

**Where it lives.** Two independent halves, both confirmed in current code.

The delete never touches descendants:

- `app/api/content/content/[id]/route.ts:1490` — `DELETE`
- `:1504-1515` — loads the node *with* `children: { select: { id: true } }`, so the child
  ids are already in hand
- `:1565-1604` — the soft-delete transaction. `contentNode.update({ where: { id } })` marks
  exactly one row; `:1585-1590` records `hasChildren` into the trash snapshot and then does
  nothing with it
- `:1620` — `cascadeOwnedDeletes` cascades the *ownership* chain (side chats, generated
  media at `:1719-1739`, conversations at `:1696-1712`, workspace pane state at `:1654-1658`).
  There is no `parentId` cascade anywhere in the handler

The tree then promotes the orphans:

- `app/api/content/content/tree/route.ts:687-700` — hierarchy pass
- `:692-699` — if a node's `parentId` is not in `nodeMap`, it is pushed onto `rootNodes`.
  The soft-deleted folder was filtered out of `nodeMap` by the `deletedAt` query, so every
  child lands at the top level

**Diagnosis.** Confirmed against both files. The promotion branch is deliberate — the
comment at `:674-684` explains it exists so a scoped view's root row can be dropped while
its children stay visible. That behaviour is correct for view roots and wrong for deleted
parents, and the two cases are indistinguishable at `:692` because both look like "parent
absent from the map".

On the regression claim: I could not identify the commit that changed this.
`git log -S "parentId: id" -- 'app/api/content/content/[id]/route.ts'` returns nothing, so
the delete route appears never to have cascaded. The likelier story is that the bug was
latent — orphans used to be dropped from the tree rather than promoted — and the view-root
promotion made it visible. Not worth chasing; the fix does not depend on it.

**Approach.** Cascade the soft-delete down the `parentId` subtree inside the existing
transaction: collect descendant ids with a recursive CTE (or an iterative level-walk over
`contentNode.findMany({ where: { parentId: { in: … }, deletedAt: null } })`), then
`updateMany` them with the *same* `now` and `deletedBy` the parent gets.

Reuse `now` verbatim, because that timestamp is also the cheapest correct answer for
restore. `lib/features/trash/service.ts:96-104` restores a single row
(`where: { id }`), so a delete cascade without a matching restore cascade would resurrect
a folder whose children stay in the trash — a new bug in place of the old one. Restoring
descendants whose `deletedAt` **equals the parent's** revives exactly the rows this delete
took, and leaves alone any child the user had trashed independently beforehand.

Rejected: (a) a `deletedRootId` / cascade-marker column — cleaner to query and it survives
clock oddities, but `prisma/` is owner-owned and this would need a migration for something
the shared timestamp already encodes. If you decide you want it anyway, that is an **owner
step**: `prisma migrate dev` plus the committed migration file, never something the fixer
just runs. (b) A database-level `onDelete: Cascade` — wrong tool twice over: these are soft
deletes, so no SQL delete fires, and `prisma/schema.prisma:163` deliberately sets
`onDelete: NoAction` on the Hierarchy relation.

One trap while you are here: purge at `lib/features/trash/service.ts:145` is also
single-node (`contentNode.delete({ where: { id } })`). With `onDelete: NoAction`, purging a
folder whose children are still live raises a foreign-key violation. Cascading the *soft*
delete makes the children trashed rather than live, which improves this — but purge order
within a subtree is still worth a look while the file is open.

**Gates.** `typecheck` → `lint` → `build`. No schema change under the recommended approach,
so no migration and no `migration-drift` exposure. Not an editor or publishing change, so
`collab:schema:check` and the publishing gates are untouched.

```markdown
- [ ] **Smoke #183:** create a folder with two files inside, delete the folder and confirm → both files disappear from the tree (not promoted to the root), and both appear in Trash alongside the folder
- [ ] **Smoke #183b:** restore that folder from Trash → the folder and both files come back nested as before; a third file trashed separately *before* the folder delete stays in Trash
```

## #193 — OpenAI chats permanently fail after ~30 days

**Reported:** 2026-08-28 · **Labels:** `bug`

**Symptom.** Any OpenAI-backed conversation older than roughly 30 days becomes permanently
unsendable — every send returns an upstream 400, `Item with id 'msg_…' not found`. Rotating
the OpenAI key reproduces it immediately without waiting.

**Where it lives.** The issue ships its own diagnosis; I verified each cited location still
matches current code.

- `app/api/ai/chat/route.ts:83-98` — `buildProviderOptions`. There is no `openai` branch
  (`:100-130` covers anthropic, google, deepseek only)
- `:98` — `if (!model || !model.reasoning) return undefined;`. This is exactly the early
  return the issue warns about: an `openai` branch added below it would never be reached by
  non-reasoning models
- `lib/domain/ai/context-diet.ts:30` — `stripReasoningForResend`, and `:76`
  `supersedeIterationHistory`. These are the two existing model-path-only transforms; the
  contract is spelled out at `:70-71` ("the persisted transcript and originalMessages keep
  every byte"). A new stripper belongs beside them and under the same contract
- Nothing in `lib/domain/ai/` references `itemId` — grepped, zero hits. That confirms step 3
  of the issue's root cause: the `openai` provider-metadata namespace is persisted and
  replayed untouched

**Diagnosis.** Confirmed live. `git log --since=2026-08-28` over the chat route,
`context-diet.ts`, `providers/registry.ts` and `lib/features/conversations/service.ts`
returns two commits, `aec686f` and `53b3459` — both the mechanical charters rename, neither
touching this path.

The mechanism is the issue's, restated: the SDK's `store` option defaults to `true`, so on
replay `convertToModelMessages` substitutes `{ type: "item_reference", id: "msg_…" }` for
text we are holding verbatim in `ConversationMessage.parts`. When OpenAI's ~30-day item
retention expires — or the key rotates, which re-scopes the store — the reference resolves
to nothing and the whole request is rejected.

**Approach.** Take the fix the owner already decided in the issue body (2026-08-28), both
halves:

1. Add an `openai` branch to `buildProviderOptions` returning `{ openai: { store: false } }`,
   placed **above** the `:98` early return. It merges with the existing `promptCacheKey`
   options through `mergeAIProviderOptions`.
2. Add a transform beside `stripReasoningForResend` in `context-diet.ts` that removes
   `openai.itemId` from both `part.providerMetadata` and `part.callProviderMetadata`, and
   wire it into the model-message chain. Model path only — never `originalMessages`.

Both are needed: (1) stops new transcripts being poisoned, (2) heals the ones already
poisoned, which is every existing OpenAI conversation.

The alternatives are already argued in the issue and I agree with the disposition: the
age-based hybrid needs a retry fallback anyway (expiry is per-message, and key rotation and
ZDR policies kill items early), which makes the age logic dead weight; and optimistic+retry
protects only upload bandwidth, since referenced items are billed as input tokens either
way and `lib/domain/ai/prompt-cache.ts` already captures the real saving. The one genuine
cost of `store: false` — reasoning models cannot reuse server-side reasoning state across
turns — is acceptable, since reasoning parts are already stripped on resend for
non-Anthropic vendors.

**Gates.** `typecheck` → `lint` → `build` → `pnpm ai:drift:check` (path-filtered onto
`lib/domain/ai/**` and the chat route, so it will fire). No migration: old transcripts keep
their dead `msg_…` ids in Postgres, harmless once stripped on the resend path.

```markdown
- [ ] **Smoke #193:** rotate the OpenAI key in Settings → AI, then send a message into an OpenAI conversation that already has assistant replies → the reply streams normally instead of failing with "Item with id 'msg_…' not found"
- [ ] **Smoke #193b:** send into a brand-new OpenAI conversation, then reload the page and send again → both turns stream normally, and the second request carries full message text rather than item references
```

## #188 — Tab right-click context menu can bleed outside the viewport

**Reported:** 2026-08-28 · **Labels:** `bug`

**Symptom.** Right-clicking the rightmost main-panel tab opens a menu that runs off the
right edge of the viewport, mostly or entirely unreachable. It also renders behind the
right sidebar when that is expanded.

**Where it lives.** `components/content/headers/MainPanelHeader.tsx`.

- `:743-747` — the handler stores the raw pointer coordinates:
  ```ts
  setTabMenu({ tabId: tab.id, x: event.clientX, y: event.clientY });
  ```
- `:839-843` — rendered inline (not portalled), `position: fixed`, `min-w-56` (224px),
  `z-50`, at `style={{ left: tabMenu.x, top: tabMenu.y }}`

No measurement, no boundary detection, no flip, no clamp.

**Diagnosis.** Confirmed. A 224px-wide menu whose left edge is the click x overflows
whenever the click lands within 224px of the right edge — which is where the rightmost tab
is by definition. `position: fixed` means nothing clips it, so the failure is silent
overflow rather than a visible cut-off, exactly as the screenshot shows.

The stacking complaint is a second, smaller defect in the same render: `z-50` is applied
inside the header's stacking context, so it cannot reliably paint above a sidebar that sits
higher in the tree. Portalling to the body (which the fix needs anyway) resolves both.

**Approach.** This is the same bug the assistant-avatar tooltip had, and it was fixed three
days before this one was filed — `0e541bd` (2026-08-27), *"fix(ai-chat): keep the assistant
detail card inside the viewport"*, closing #179. Copy that recipe: portal to the body,
two-phase measure-then-position (render hidden at the raw anchor, measure, place), and
delegate placement to `calculateMenuPosition` in `lib/core/menu-positioning.ts:77`, with
`anchorMenuAbove` (`:187`) for the vertical flip.

`CLAUDE.md`'s "prefer the existing library over a bespoke build" rule points straight at
this: the repo now owns this positioning logic in one place and uses it from the context
menus, the dropdowns and the chat tooltip. A hand-rolled `window.innerWidth` check here
would be the fourth copy.

Rejected: clamping `left` to `innerWidth - width`. One line, but it slides the menu over the
tab the user right-clicked, and it leaves the sidebar stacking half of the report unfixed.

**Gates.** `typecheck` → `lint` → `build`. Positioning is inline style, not CSS, so no
`.dark` companion is needed — but the menu already carries explicit light/dark classes at
`:841`, so confirm both themes still read correctly after the portal move.

```markdown
- [ ] **Smoke #188:** with the right sidebar expanded, right-click the rightmost main-panel tab → the menu opens fully inside the viewport, flipped leftward from the pointer, and paints above the sidebar rather than behind it
```

## #83 — Copying a checklist or text inside a column pastes the whole column

**Reported:** 2026-06-22 · **Labels:** `bug`, `Content Note`, `Blocks`, `Checklists`

**Symptom.** Select only the text (typically checklist items) inside the left column of a
two-column block, copy, then paste into ordinary prose — the column block comes with it
instead of just the content.

**Where it lives.** The node specs, in both column families.

- `lib/domain/editor/extensions/blocks/columns.ts:62-66` — `Column`: `defining: true`,
  `isolating: true`
- `:85-89` — `Columns`: `defining: true`
- `lib/domain/editor/extensions/blocks/block-columns.ts:73-76` and `:148-151` — `blockColumn`
  / `blockColumns`, the same two flags again
- Server variants carry the identical specs: `columns.ts:360-363` and `:379-382`,
  `block-columns.ts:389-392` and `:408-411`

Not the clipboard extension: `lib/domain/editor/extensions/clipboard.ts:81-90` overrides
only `clipboardTextSerializer` (the plain-text flavour). The rich HTML slice — the one that
carries the wrapper — never passes through it.

**Diagnosis.** Two ProseMirror flags, each sufficient to produce part of the symptom.

`defining` on `column`/`columns` is the direct cause of the paste half: a defining node is
treated as important context for the content it holds, so when that content is pasted
elsewhere ProseMirror re-creates the wrapper around it rather than letting the slice flatten
into the target.

`isolating: true` on the column is the likely cause of the copy half. It makes the column a
hard selection boundary, so a selection covering all of a column's content tends to widen to
the column node itself — meaning the wrapper is in the slice before paste is even reached.
That also explains why the reporter hit this with checklist items, which are easy to select
exhaustively.

**Approach.** `defining` is shorthand for two independent ProseMirror flags. Split it: keep
the one that protects a column's own content when something is pasted *into* it, and drop
the one that carries the column *out* when its content is pasted elsewhere. That is a
one-line change per node spec, applied identically to the client and server variants in both
files.

Verify the flag split against the installed `prosemirror-model` before writing it — I could
not: `node_modules` is not installed in the triage container, so I could not read the
typings to confirm which of `definingAsContext` / `definingForContent` carries which
behaviour in the pinned version. Getting this backwards inverts the fix, so read the
`NodeSpec` typings first. That check is a few minutes with dependencies installed, which is
why this is a medium-confidence plan rather than a blocker.

Leave `isolating` alone on the first pass. It is load-bearing for editing behaviour inside
columns (backspace and lift should not cross a column wall), and if the `defining` split
alone fixes the reported repro, the selection-widening half was never the operative cause.
Only revisit it if paste is fixed and copy still drags the wrapper.

Rejected: a `transformPasted` handler that unwraps column nodes on paste. It works, but it
fixes the symptom at the destination while leaving the wrong slice on the clipboard — so
pasting into another app, or into a different editor surface, still carries the column. Fix
the node spec, not the paste site.

Schema note: changing a flag on an existing node is not a new node or mark, so no `Server*`
registration work — but the specs are duplicated across four places in two files, and all
four must move together or client and server disagree. `pnpm collab:schema:check` will not
catch a flag divergence, only a missing registration, so check by eye. Consider a MINOR bump
of `TIPTAP_SCHEMA_VERSION` per `lib/domain/editor/schema-version.ts`: no stored document
changes shape, so it is arguably unnecessary — make the call explicitly rather than by
omission.

The reporter lists untested neighbours: second column, three-column, block-within-block, and
the tabs block. Tabs are worth checking specifically — `blocks/tabs.ts` is the same
container shape and may carry the same flags.

**Gates.** `typecheck` → `lint` → `build` → `pnpm collab:schema:check` (runs inside `build`;
this touches TipTap extension source, so the collab gate is in scope) → `pnpm markdown:blocks:check`
(the columns codec round-trip could be affected by a spec change).

```markdown
- [ ] **Smoke #83:** in a two-column block, select just the checklist items in the left column, copy, and paste into a plain paragraph below the block → only the checklist items paste, with no column wrapper
- [ ] **Smoke #83b:** repeat from the right column of a three-column block, and from a checklist inside a tabs block → same result, no wrapper
- [ ] **Smoke #83c:** copy an entire column block by selecting it from outside, paste → the column block still pastes intact (no regression in copying the block itself)
```

## #64 — Content page position is not persistent across tab navigation

**Reported:** 2026-06-12 · **Labels:** `bug`, `Content Note`, `Workspace Pane`

**Symptom.** Scroll down a long note, switch to another tab in the same pane, switch back —
the note is back at the top, after a skeleton flash.

**Where it lives.** The pane renders only the active tab's content, so a tab switch is a
full remount.

- `components/content/content/MainPanelContent.tsx:445-459` — the surface is keyed by the
  active tab: `viewInstanceId: \`${paneId}:${activeTabId ?? selectedContentId ?? "empty"}\``,
  with `activeTabId` in the dependency array at `:458`. Inactive tabs are not mounted
- Nothing persists scroll offset anywhere in `components/content/` or `state/`. Grepping
  `scrollTop|scrollRestor|scrollPosition` across both returns only unrelated consumers — the
  JSON viewer's gutter sync (`viewer/JSONViewer.tsx:130`), the data table's virtualiser
  (`data/DataTableViewer.tsx:119`), the reasoning disclosure's scroll nudge

**Diagnosis.** Confirmed by absence: there is no scroll-restoration mechanism to be broken.
The reporter's own guess in **Additional context** — "the page shows a loader skeleton and
may be rerendering between tab navigations" — is right, and `:451` is why.

**Approach.** Add a small scroll-offset cache and restore from it on mount. Key it by
`paneId:contentId` rather than `paneId:tabId`, so the position survives a tab being closed
and the same note reopened in the same pane, which is what "last-viewed position" means to a
user. Write on scroll (throttled, or on a `scrollend`-style idle) and on unmount; read after
the content has settled, not on first paint, or you will restore against a zero-height
container and land back at the top.

Session-scoped state, per the issue's own framing ("for that user's browser session"), with
the bounds it asks for: a fixed entry ceiling with least-recently-viewed eviction. A plain
`Map` in a Zustand store is enough — this does not need to survive a reload, so it does not
need `persist`, which also sidesteps unbounded localStorage growth.

Rejected: (a) keeping every tab mounted and toggling visibility. It fixes scroll for free
and kills the skeleton flash too, but it multiplies live editors, collaboration providers
and their sockets by the tab count — far too much blast radius for a scroll bug, and it
would want its own plan. (b) The browser's native scroll restoration: it is scoped to
history navigation, and these tab switches are not history entries.

Note the issue also asks to "avoid loader skeleton". Treat that as out of scope here — it is
the remount, i.e. rejected option (a). Fixing the scroll position without touching the
mounting model is the cheap 80%, and worth confirming with the owner that it is enough
before anyone reaches for the keep-alive rework.

**Gates.** `typecheck` → `lint` → `build`. Watch `react-hooks/exhaustive-deps` on the
restore effect, and the React Compiler's "cannot access refs during render" rule — the
scroll write belongs in an effect or event handler, never in render. No new CSS, so no
`.dark` companion.

```markdown
- [ ] **Smoke #64:** open a note longer than the viewport plus a second note in the same pane, scroll the first note halfway down, switch to the second tab and back → the first note is still at the halfway position, not the top
- [ ] **Smoke #64b:** close the first tab, reopen the same note in that pane → it restores to the same position; open it in a *different* pane → that pane starts at the top
```
