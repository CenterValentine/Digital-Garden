## #319 — Editor jumps to top when collaboration sleeps or wakes

**Reported:** 2026-11-18 · **Labels:** `bug`, `Content Note`, `hocuspocus`, `collaboration`

**Symptom.** While scrolled partway down a note, the view snaps back to the top of the
document and the caret/selection is lost. It coincides with the collaboration status
signal at the top of the note changing. Found during the desktop-shell M0 smoke (Electron,
prod), but the mechanism is in the web app — two windows on one note only made it easy to
trigger.

**Where it lives.** The editor is recreated whenever the Hocuspocus provider appears or
disappears:

- `components/content/editor/MarkdownEditor.tsx:486-490` derives `editorMode` from
  **provider presence** — `collaborationState.provider ? "collaboration" : "collaboration-local"`.
- `components/content/editor/MarkdownEditor.tsx:1022` makes `editorMode` a `useEditor` dep:
  `}, [editorMode, collaborationDocument]);`
- `lib/domain/editor/extensions-client.ts:201-203` is *why* that dep is honest today:
  `CollaborationCaret` is included **only** when `collaboration.provider` is truthy, so the
  extension set itself changes with provider presence, and TipTap takes extensions at
  creation. `Collaboration.configure` (`:197-200`) does not depend on the provider — only
  the caret does.
- `lib/domain/collaboration/runtime.ts` tears the provider down on ordinary timers:
  `maybeStartCooldown` (`:2679`, solo + synced for `COOLDOWN_MS = 120_000` at `:431`) and
  `maybeEnterSleepMode` (`:2708`, `VISIBILITY_SLEEP_DELAY_MS` 3 min hidden /
  `INACTIVITY_SLEEP_DELAY_MS` 10 min idle at `:437-438`) both call `destroyProviderOnly`
  (`:2833-2837`), which sets `entry.hocuspocusProvider = null`.
- `components/content/headers/MainPanelHeader.tsx:58-61` (`ACTIVE_TRANSPORT_STATES`) flips
  on the same transitions, which is the observed correlation.

**Diagnosis.** Confirmed against current code; no commit has touched either file since the
issue was filed (`git log --since=2026-11-18 -- components/content/editor/MarkdownEditor.tsx lib/domain/collaboration/runtime.ts`
is empty). Provider null → `editorMode` flips → `useEditor` rebuilds → new ProseMirror DOM,
so the scroll container's content height momentarily collapses and the browser clamps
`scrollTop` to 0. Promotion on wake, or a second window joining, flips it back and
recreates again.

**The part the issue does not claim — the reset is also persisted.** Viewport memory
(`lib/domain/content/use-viewport-memory.ts`, mounted for notes at
`components/content/editor/MarkdownEditor.tsx:1164`) is the "leave a tab, come back to the
same spot" mechanism, and this recreate corrupts it:

1. Its restore effect is keyed `}, [contentId, region, enabled]);` (`:147`). A provider flip
   changes **none** of those, so no restore runs.
2. Therefore `suppressRef` (`:59`, set only while a restore is pending, `:86`) is `false`
   when the clamp-to-0 fires a real `scroll` event.
3. `handleScroll` (`:61-67`) then calls `recordViewport(contentId, region, 0)`, and
   `recordViewport` accepts 0 — it rejects only non-finite and negative offsets
   (`lib/domain/content/viewport-memory.ts:136`).

So the remembered offset is replaced by 0, and the *next* return to that tab also lands at
the top. That is #64's reported symptom, which is why I am claiming the tie-break-2
promotion: whoever fixes #319 should expect part of #64 to move with it. #64 is already
planned in a prior doc and is **not** re-planned here.

**Approach.** Treat an editor recreate as a "content just (re)arrived" event for viewport
memory, and stop the clamp from being recorded. Two parts, both inside the existing hook
rather than a parallel mechanism:

1. **Never record an offset measured against a container with nothing to scroll** — guard
   `handleScroll` on `scrollHeight > clientHeight`. A 0 measured against an empty container
   is never a real reader position. This is the load-bearing half: it stops the memory
   poisoning regardless of effect ordering, and it hardens #64 on its own.
2. **Re-run the restore when the editor instance changes** — give `useViewportMemory` an
   optional epoch (pass `editorMode`, or a counter bumped when `editor` identity changes)
   and add it to the restore effect's deps. The existing retry-across-frames loop
   (`:97-139`) already handles exactly this case; its own comment cites "a collaborative
   note's Y.Doc materializes after the editor is recreated".

Part 1 before part 2: ordering makes part 2 a race (the clamp can fire before a
re-triggered restore sets `suppressRef`), and part 1 is what makes that race harmless.
Caret/selection restoration is a separate, smaller follow-up — snapshot
`editor.state.selection` before teardown and reapply after mount — and should not be
bundled in until the scroll half is verified.

*Alternative 1 — stop recreating on provider presence (the issue's direction 2).* The
right long-term fix, and explicitly **not** proposed for this pass. It requires
`CollaborationCaret` to attach and detach on a live editor, where today the extension set
changes (`extensions-client.ts:201-203`) and TipTap binds extensions at creation. Doing it
properly means either an upstream-shaped change or registering the caret permanently
against a stable provider indirection with awareness swapped underneath — which risks
leaked awareness listeners and stale remote carets, a worse class of bug than the one being
fixed. It also sits one dep away from `collaborationDocument`, which is load-bearing (the
2026-10-06 wrong-Y.Doc report, documented at `MarkdownEditor.tsx:1003-1014`). Keep that dep
whatever else changes.

*Alternative 2 — don't demote a visible, focused note (the issue's direction 3).* Rejected
as a fix, though reasonable as a later policy tweak: it reduces frequency but leaves the
most reproducible trigger untouched, because opening the same note in a second window
*promotes* and recreates just the same. It also makes the cooldown's purpose — dropping
idle sockets — conditional in a way that needs its own design pass.

**Nothing here touches Y.Doc identity**, so `CONTENT-LOAD-CASCADE.md` §9.4 is satisfied by
construction: no payload write, no reseed. No new TipTap node or mark, no publishing block,
no schema change, and no new CSS, so `collab:schema:check`, the `Server*`-variant rule, the
migration gate and the dark-mode companion rule are all out of scope.

**Gates.** `pnpm typecheck` → `pnpm lint` → `pnpm build`. The build chain's
`workspace:cold-load:smoke` and `workspace:pane-placement:smoke` are the ones that can
plausibly catch a regression from this change, since both exercise content mount and
restore; run the full `build` rather than the two in isolation. No static gate is specific
to this area, so the browser smoke is the real verification:

```markdown
- [ ] **Smoke #319:** scroll halfway into a long note, then open that same note in a second window → the first window keeps its scroll position instead of jumping to the top, and switching to another tab and back returns to that same position
```

**Why that is a named cause and not an impression.** The AI `@` picker fetches
`/api/content/content?search=…&limit=16` with no `offset`
(`lib/domain/ai/use-conversation-engine.ts:1676-1678`), so it takes the tiered path
(`offset === 0`) and Tier 1 is an exact, case-insensitive title match. The pre-fix
behaviour explains the issue's specifically *one-word* framing: the OR-clause matched body
text while ordering alphabetically, so a short common word like "Services" filled all 16
slots with notes whose *content* contained it before the folder literally *named* it
appeared. A multi-word folder name is rare in body prose and so was never crowded out.
Folders are not excluded (the picker sends no `type`, and `contentType` is constrained only
when `type !== "all"`, `app/api/content/content/route.ts:155-158`), nothing filters them
client-side (`components/content/ai/ChatInput.tsx:378-387` passes `mentionResults` through
untouched), and every tier is `mode: "insensitive"`, which answers the issue's
case-sensitivity aside. The issue's request to "check for file name regressions" is covered:
the tiering is content-type agnostic.
